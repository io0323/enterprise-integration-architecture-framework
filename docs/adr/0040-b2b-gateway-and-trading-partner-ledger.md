# ADR-0040: B2B Gateway と取引先の台帳(TPA)
- Status: Accepted
- Date: 2026-10-31
- Framework 参照章: 11.1, 11.2, 11.3, 12, 13, 14.1, 16
- 関連: ADR-0008(B2B のプロトコルは SFTP だけ)、ADR-0017(監査)、ADR-0032(ファイル連携の部品と、P09 の取引先の台帳)、ADR-0041(EDIFACT のサブセットと応答)
- 番号: P12 の計画で予約した番号(0040 B2B Gateway / 0041 EDIFACT)。0041 を先に書いたため、一時的に番号が飛んでいた

## Context
P12(B2B / EDI Gateway。#15)では、取引先との送受信を b2b-gateway に集める。Framework 11.1 は、送受信は必ず B2B Gateway を通し、取引先の台帳(識別子・証明書・プロトコル・ドキュメント種別・SLA・担当者。証明書の期限を監視)と TPA(フォーマット・コード体系・再送の規則・締め時刻・障害時の連絡)を持つことを求めている。11.3 のアンチパターンは「原本保管なし」「証明書期限切れ放置」「997/MDN 未確認運用」。

P09 では、file-exchange が日次の売上ファイルを取引先に直接 SFTP で送り、送り先を取引先の ID ごとの台帳(`infra/local/file-exchange/partners.json`)に持っていた(ADR-0032 §8。「P12 の B2B Gateway の台帳に、この形のまま引き継ぐ」)。

P12 の計画(承認 2026-10-30)で次を決めた。
- **判断 1(案 1)**: 取引先への送信を file-exchange から b2b-gateway に移す(⑦)。台帳は 1 か所に持つ。
- **判断 3(案 A)**: 受注の文書を Canonical の注文に変えた後、order の API(Gateway 経由)で社内に渡す(⑤)。
- 承認の条件 2: 原本の保持期間と法令の関係を、この ADR に書く。
- 承認の条件 3: 売上ファイルの送信と、CONTRL・APERAK の送信を、同じ送信の仕組みにまとめる(⑦)。

この ADR は ③ で書き、受け取り(④)・社内への取り込み(⑤)・送信の移管(⑦)で改訂する。

## Decision

### 1. b2b-gateway の範囲
- 取引先との送受信の境界(Framework 11.2)。受け取り(SFTP)→ 原本の保管と監査 → 3 段階の検査と応答(ADR-0041)→ Canonical への変換と社内への取り込み、と、取引先への送信(売上ファイル・応答)を受け持つ。
- サービスの中の部品の分け方は MODULE_DESIGN の b2b-gateway の行に書く。

### 2. 取引先の台帳: 1 つのファイルと、1 つの読み込みの部品(P12 ③)
- **台帳は 1 つのファイル**(ローカル基盤は `infra/local/b2b/partners.json`。`make env` がテンプレートから作る。§3)で、**読み込みと検証は `platform/trading-partner` の `TradingPartnerLedger` だけ**が行う。b2b-gateway と、送信を移すまでの file-exchange が、同じファイルを同じ部品で読む。同じ取引先の情報を 2 か所に持たない。
  - P09 の `infra/local/file-exchange/partners.json` はこのファイルに移した。file-exchange の `PartnerRegistry` は、台帳からファイルの送り先(`PartnerDestination`)を作るだけの変換になった。
  - 部品を platform に置いたのは、送信を移すまでの間に 2 つのサービスが同じ台帳を読むため。⑦ の後は b2b-gateway だけが読むが、台帳は B2B の基盤の部品として platform に残す。
- **形は JSON Schema**(`platform/trading-partner/src/main/resources/trading-partner/ledger.v1.schema.json`)。読み込みの順は、形 → 値の解釈(日付・期間・タイムゾーン)→ 取引先の重複と、扱う文書ごとに要る設定。誤りは項目の場所(JSON Pointer)と理由で返し、値は入れない。台帳の誤りは起動時に設定の誤りにする。
- **台帳の項目**(Framework 11.1 の台帳と TPA)

  | 項目 | 内容 |
  |---|---|
  | `company` | 自社の識別子(UNB の受け手と、注文の NAD+SU の GLN) |
  | `id`・`name` | 取引先の ID(メトリクスの属性と Resilience の名前に使う。英小文字・数字・ハイフンの 32 文字まで)と名前 |
  | `edifact` | 取引先が送る交換の UNB の送り手(識別子と識別の機関)。届いた交換の送り手が違えば 0085 = 23(ADR-0041 §11) |
  | `documents` | 扱う文書。連携カタログの ID と向き(ファイルは `dataset` も)。カタログの粒度は「文書の種類 × 向き」(ADR-0041 §7) |
  | `sftp` | 接続先・ホスト鍵(known_hosts の秘密情報の名前と期日)・クライアントの鍵(秘密情報の名前と期日)・ディレクトリ(`outbound`・`inbound`・`acknowledgements`)・書き終わりの判断(§4) |
  | `pgp` | 取引先の PGP の公開鍵(秘密情報の名前と期日) |
  | `agreement` | 通貨・肯定の APERAK を返すか・業務の応答(APERAK)の期限(承認の条件 1)・締め時刻とタイムゾーン・CONTRL の SLA・再送の規則 |
  | `contacts` | 連絡先(`business`・`operations`・`incident`)。個人ではなく役割の窓口を書く |

- **扱う文書ごとに要る設定**: 文書を受け取る取引先には `edifact`・`sftp.directories.inbound`・`sftp.completion`、ファイルを送る取引先には `sftp.directories.outbound` と `pgp`(取引先への経路では暗号化が必須。ADR-0032 §8)、応答を返す取引先には `sftp.directories.acknowledgements` が要る。
- **台帳とカタログの照合**: 台帳の文書がカタログにあり、EDI(`style: edi`)かファイル(`style: file`)の連携で、受け取る文書の送り手がカタログで取引先(`provider.system: trading-partners`)であることを、`platform/trading-partner` のテストがローカル基盤の台帳で確かめる(`./gradlew build` で動く)。
  - contract-check では検査しない。台帳は契約(`contracts/`)ではなく、環境ごとの設定(本番の台帳は本番の設定の置き場)のため。
- **秘密情報は名前だけを書く**(値は `SecretProvider` から読む。ADR-0019 §6)。ホスト鍵は秘密ではないが、鍵と同じく差し替えるので秘密情報として読む(ADR-0032 §8 と同じ)。
- 台帳は起動時に読む。台帳の変更は、鍵の差し替えと同じく運用の手順(docs/runbooks/b2b-partner-credentials.md)で行い、読むサービスを再起動する。
- b2b-gateway は、台帳から受注の文書を受け取る取引先の合意(`PartnerAgreement`。ADR-0041 §11)を作る(`LedgerPartnerAgreements`)。合意した通貨が知らない通貨(小数桁数がわからない)なら設定の誤り。

### 3. 鍵とホスト鍵の有効期限の監視(P12 ③)
- **SSH の鍵とホスト鍵そのものには期限がない**。そこで、TPA で合意した差し替えの期日(`validUntil`)を台帳の必須項目にし、その期日で監視する。期日は、その日の終わり(UTC)まで有効とする。
- **PGP の公開鍵は、台帳の期日と、鍵の中の期限(主鍵と暗号化の副鍵のうち早いほう)のうち早いほう**で監視する。鍵を読むのは Bouncy Castle を使ってよい `platform/file-transfer`(`PgpKeys.publicKeyExpiry`)なので、`platform/trading-partner` は鍵の中の期限の読み方を受け取る(`EmbeddedExpiry`)。鍵を読めなければ台帳の期日で監視する(読めない鍵は送信のときに鍵の誤りになる)。
- **メトリクス** `eia.trading_partner.credential.expiry`(期限の UNIX 秒。属性 `trading_partner.id`・`trading_partner.credential` = `sftp_host_key` / `sftp_client_key` / `pgp_public_key`)。読み出しのたびに求め直す(鍵の差し替えに追従する)。台帳を読むサービスが出す。
- **アラート**(`infra/local/prometheus/rules/trading-partner.rules.yml`。promtool のテスト付き): 残り 30 日で警告、7 日で重大、過ぎたら重大。2 つのサービスが同じ系列を出すので、取引先と鍵の種類ごとの最小値で判定する。手順は docs/runbooks/b2b-partner-credentials.md。
  - 30 日と 7 日は、取引先と差し替えの日程を合わせる時間(数週間)と、差し替えを急ぐ時間から決めた。取引先との合意で変えるときは、ルールを改訂する。

### 4. 受け取り(P12 ④b1)
- **取引先の SFTP サーバの受け取りのディレクトリ(`inbound`)を、b2b-gateway が見に行く**(pull)。ローカルでは sftp-b2b の partner01(P09 と同じ役割)。P09 の送信と同じ接続の設定・ホスト鍵の固定を使う。自社が SFTP サーバを持ち、取引先が置く形(push)は、本番の選択肢として残す。
- **取引先は、ファイルを置いた場所で決まる**。届いた交換の送り手は、その取引先の台帳の識別子と照らし合わせる(ADR-0041 §11)。
- **書き終わりの判断**(取引先はマニフェストを置かない前提)は、取引先ごとに台帳で選ぶ。
  - `rename`(既定): 取引先は一時名(`temporarySuffix`。例 `.part`)で書き、正式名に変える。正式名だけを拾う。
  - `stable`: 前の見回りから大きさと更新の時刻が変わっておらず、更新の時刻から `quietPeriod` が経ったファイルだけを拾う。前の見回りの観測はメモリに持つ(再起動の後の最初の見回りでは拾わない)。推測に頼るので、TPA では `rename` を勧める。
  - ~~どちらでも、EDIFACT の UNZ(件数と管理番号の一致)を中身による完了の検査にし、UNZ がなければ書いている途中とみなす(待ちの上限を過ぎたら構文の誤り。ADR-0041 §2)。~~ **EDI の文書に PGP を使うことにした(§8)ので、この検査はしない**。UNZ は暗号文の中にあり、書きかけの暗号文は復号できない。書きかけのまま拾った暗号文は、復号の段階で拒否する(`pgp_malformed` など。原本と監査は残る)。復号した交換に UNZ がなければ、取引先が書きかけの交換を暗号化したもので、待っても届かないので、構文の誤り(0085 = 13 / UNZ)として CONTRL で返す。
- **受け取りのディレクトリの使い方**(`SftpPartnerInbox`。`platform/file-transfer` の `SftpReceiver` で、P09 の送信と同じ接続を使う)

  | ディレクトリ | 置くもの |
  |---|---|
  | `{inbound}` | 取引先が置いたファイル |
  | `{inbound}/processing` | 押さえたファイル(処理が終わるまで) |
  | `{inbound}/processed` | 処理が終わったファイル(`{受け取りの記録の ID}-{名前}`。同じ名前の送り直しとぶつからない) |

  - **押さえは名前の変更**(受け取りのディレクトリ → 処理中)。名前の変更はサーバの中で不可分なので、2 つの処理が同じファイルを押さえない(元がなければ、ほかの処理が先に押さえた)。
  - **見回り**(`PollInboxUseCase`)は、前の処理が押さえたまま落ちたファイル(処理中のディレクトリに残ったもの)を先に処理し、それから書き終わったファイルを押さえて、1 つずつ受け付ける(§5)。受け付けが終わったら(受け取りの記録と監査を書いたら)処理済みに移す。読めない文書も記録してから処理済みに移す。
  - 1 つのファイルの失敗(DB や S3 に書けない)は、ほかのファイルの処理を止めない。失敗したファイルは処理中に残し、次の見回りで続きから処理する(受け付けはやり直しても収まる。§5)。処理中に残り続けるファイルは、アラートにする(⑥)。
  - 1 つの文書の大きさの上限は 16 MiB(B2B の文書は小さい)。超えたファイルは読まずに失敗にし、処理中に残す(運用で取引先と確かめる)。
  - SFTP の呼び出しは、取引先ごとの Resilience(`sftp-{取引先の ID}`。送信と共有する。app で作る)で包む。
  - 見回りの間隔と、台帳の取引先ごとの見回りの結線は app(⑥)。ローカル基盤の sftp-b2b の受け取りと応答のディレクトリも ⑥ で作る。
- 交換の重複(EDI の層での冪等)は ADR-0041 §11。

### 5. 原本の保管と、保持期間・法令(P12 ④a)
- 受け取った原本は、**解析の前に、手を加えずにバイト列のまま**(PGP の暗号文。§8)、S3 互換ストレージ(SeaweedFS)の Object Lock(COMPLIANCE)で保管する。送った応答(CONTRL・APERAK)も原本として保管する(Framework 11.1「全ドキュメントを原本保管」)。
  - 置き方は `platform/file-transfer` の `LockedObjectWriter.putLocked`(保持のモードと期限を put のたびに明示し、バケットの既定の保持設定に頼らない。ADR-0017 §5 と同じ)。同じキーに置き直すと新しい版になる。
  - キーは `originals/{取引先}/received/{原本の SHA-256}.pgp`・`originals/{取引先}/sent/{contrl・aperak}/{SHA-256}.pgp`。後から読むための写しは `readable/...`(§8)。参照は `{キー}#{版の ID}`。
  - **順番**: 原本の保管 → 復号と署名の検証 → 写しの保管 → 3 段階の検査 → 応答の暗号化と保管 → 受け取りの記録・受け付けた注文・送る応答・監査を 1 つのトランザクション(`AcceptDocumentUseCase`)。どこで落ちても、同じファイルでやり直せば収まる(原本と写しは版が増えるだけ。記録の前なら、重複の判定は初めての受け取りのまま)。2 つの処理が同じ交換を同時に記録したときは、初めての受け取りの一意索引で片方を一時的な失敗にし、やり直しで送り直しとして扱う。
- 原本の SHA-256 を `platform/audit` の監査のチェーンに記録する(ADR-0017。action `b2b.document.receive`・`b2b.ack.send`)。原本を書く S3 の資格情報は、ほかの用途と分ける(Issue #6 のコメント。⑥)。
  - **受け取ったすべての文書を記録する**(DoD)。読めない文書(§8)も、構文の段階で拒否した交換も、送り直しも、受け取りの記録 1 行と監査の記録 1 件を、同じトランザクションで書く。監査の追記に失敗したら、受け取りの記録も残さない。
  - 監査の項目: 誰が = `partner` / 取引先の ID、何を = `b2b.document.receive` / `b2b_document` / 受け取りの記録の ID、結果 = 交換の枠を受け付けた・送り直しなら `success`、拒否・読めないなら `failure`、本文の代わり = 原本(暗号文)の SHA-256 と場所、補足 = 段階(`decryption`・`syntax`・`schema`・`business`・`none`)・復号した交換の SHA-256・交換の管理番号・メッセージの数と拒否の数・拒否した注文の数・拒否の理由(読めない文書)。
- **保持期間は設定で決め、このリポジトリでは決めない**(ローカル基盤は検証を繰り返すために短くする)。
- **本番の保持期間と検索の要件は、担当部門が法令を確認して決める**(承認の条件 2)。
  - 取引の記録の保存を求める法令(日本では電子帳簿保存法の電子取引の保存など)は、保存の期間に加えて、**取引の年月日・金額・取引先で探せること**などの検索の要件を求めることがある。どの法令のどの要件が当てはまるかは、取引の種類と会社の状況で変わるので、担当部門(経理・法務)が確認して決める。
  - **原本のハッシュ(SHA-256)と監査の記録が、その土台になる**。原本が Object Lock で消せず、ハッシュが改竄を検出できる監査のチェーン(ADR-0017)にあることで、保存した原本が受け取ったものと同じことを示せる。検索の要件(年月日・金額・取引先)は、受け取りの記録(取引先・受け取りの時刻)と、取り込んだ注文(注文日・金額)を原本の参照と結ぶことで満たす形を想定する。
  - **P12 では法令の要件そのもの(検索の仕組み・保存の期間の既定値・訂正削除の防止の規程など)は実装しない**。決まった要件を満たすための仕組みは、要件が決まったときに ADR を書いて足す。

### 6. 社内への取り込み(P12 ⑤ で詳しくする)
- 受注の文書を Canonical の注文に変え、**order の API(Gateway の `/sales/v1/orders`、クライアント `eiaf-b2b-gateway`、スコープ `sales.order:write`)で社内に渡す**(計画の判断 3。案 A)。order-service の DB を直接書くのは Shared Database になるので行わない。
- Idempotency-Key は、交換の管理番号とメッセージの参照番号から毎回同じ値になるように作る(`b2b:{取引先}:{0020}:{0062}`)。受け付けの時点で、変換した要求の本文を固定し、送り直しでは同じバイト列を送る(本文の指紋が変わらないように)。
- order の Idempotency-Key は 24 時間しか保存されないので、EDI の層の重複の判定(ADR-0041 §11)を主な防御にし、送信待ちのリトライには 24 時間より短い上限を設ける。
- 肯定の APERAK は、order の API が受け付けた後に返す(ADR-0041 §5)。業務の応答の期限(台帳の `aperakDeadline`)に近づいた送信待ちはアラートにする(承認の条件 1)。
- **コードの対応表**(P12 ⑤a): 取引先ごとに、b2b-gateway の DB に 3 つの表を持つ。order の API の要求に要る社内の値は、すべてここから引く。
  | 種類 | キー → 値 |
  |---|---|
  | `buyers` | 買い手の GLN(NAD+BY)→ 社内の顧客の ID と既定の届け先(NAD+DP がない注文の届け先。仕様の ORD002) |
  | `delivery-parties` | 届け先の GLN(NAD+DP)→ 届け先の住所 |
  | `items` | 取引先の商品コード(PIA の BP)か GTIN(LIN)→ 社内の商品(productId・sku) |
  - 表は運用者のコマンド `codes import <取引先> <種類> <CSV>`(結線は ⑥)で、**種類ごとに丸ごと入れ替える**。行ごとの追加・変更はしない(取引先から受け取る表と、DB の中身を一致させやすくするため)。
  - ファイルは UTF-8 の CSV で、1 行目が見出し(列は種類ごとに固定。Runbook)。形式(GLN 13 桁・GTIN 8/12/13/14 桁・国 2 文字)・必須・長さ・キーの重複・空の表を検査し、誤りが 1 つでもあれば何も変えない。誤りは行の番号・列の名前・理由だけで返す(顧客の住所などの値を出さない)。
  - 入れ替え・版(取引先と種類ごとに 1 ずつ進める)・監査 `b2b.codes.import` を 1 つのトランザクションで書く。監査の項目: 誰が = `user` / 運用者、何を = `b2b.codes.import` / `b2b_code_table` / `{取引先}/{種類}`、本文の代わり = 取り込んだファイルの SHA-256、補足 = 取引先・種類・版・行の数。どのファイルで、いつ、誰が表を変えたかを、監査のチェーンで追える。
  - 対応表は契約(`contracts/`)には置かない。取引先との連携の形ではなく、運用者が管理する社内のマスタの写しだから。
  - 業務の検査(ADR-0041 §4)は、受け付けの時点の表で引く。社内への取り込みで使う要求の本文は、受け付けの時点で固定する(⑤b)ので、その後に表を入れ替えても、送信待ちの注文の中身は変わらない。

### 7. 取引先への送信(P12 ④b2。売上ファイルは ⑦)
- 取引先への送信を file-exchange から b2b-gateway に移す(Framework 11.1「送受信は必ず B2B Gateway 経由」)。file-exchange は合格の売上ファイルを b2b-gateway に渡すだけにする(⑦)。
- **売上ファイルの送信と、CONTRL・APERAK の送信は、同じ送信の仕組みにまとめ、送信の経路を 2 つに分けない**(承認の条件 3)。取引先ごとの設定(台帳)・PGP・Resilience(`sftp-{取引先の ID}`)・送る前の正式名の確認による重複の防止(ADR-0032 §8)を共有する。
- 送信の仕組みは application の Port `PartnerOutbox` が 1 つで、adapters の実装は `SftpPartnerOutbox` だけ(④b2)。
  - 送り先: 台帳の `sftp.directories` の `outbound`(送るファイル)か `acknowledgements`(応答)。
  - PGP: 暗号化と署名が済んでいない文書は、ここで取引先の公開鍵あてに暗号化し、自社の鍵で署名する。応答は受け付けのときに暗号化して原本として保管している(§5)ので、**保管した暗号文をそのまま送る**(送ったものと原本が同じバイト列になる)。
  - Resilience: 確認と送信を 1 回の試行にし、取引先ごとの Resilience(受け取りと共有)で包む。やり直しでは確認からやり直す。
  - 重複の防止: 送る前に取引先の側に同じ正式名のファイルがあるかを確かめ、あれば送らない(前の送信が、送った印を付ける前に落ちた)。送るときは一時名(`.part`)で書いてから正式名に変える。
- 応答の送信(`SendAcknowledgementsUseCase`。④b2):
  - 受け付けのときに送信待ち(`b2b.acknowledgement`。`state = PENDING`)で記録した応答を、古い順に送る。取引先の側の正式名は `{contrl・aperak}-{応答の記録の ID}.edi.pgp`。
  - 保管した原本を記録の版のまま読み、SHA-256 を記録と照らし合わせてから送る(置き場の誤りで違うものを送らない)。
  - 送った印(`SENT`・正式名・取引先の側にすでにあったか)と監査(`b2b.ack.send`)を 1 つのトランザクションで書く。監査の項目: 誰が = `service` / `b2b-gateway`、何を = `b2b.ack.send` / `b2b_acknowledgement` / 応答の記録の ID、どこへ = `partner:{取引先の ID}`、本文の代わり = 送った原本の SHA-256 と場所、補足 = 種類・受け取りの記録の ID・正式名・すでにあったか。
  - 1 件の失敗はほかの応答を止めない。失敗した応答は送信待ちのまま残し、次の回に送る。2 つの処理が同じ応答を送っても、正式名が同じなので二重には届かず、先に印を付けたほうだけが監査を書く。
  - 送り直しの交換(§4・ADR-0041 §11)には、前の応答と同じ原本を指す新しい記録ができるので、新しい正式名でもう一度届く。
  - 送る間隔と、送れない応答のアラート(業務の応答の期限を含む)は ⑤・⑥ で決める。

### 8. B2B の文書の PGP(P12 ④a。承認 2026-10-31)
- **EDI の文書にも PGP を使う**(Framework 9.2「ファイル自体の暗号化(PGP 等、B2B・機密は必須)」。ADR-0032 §8 の「取引先への SFTP の経路では必須」と揃える)。取引先は ORDERS を自社の公開鍵あてに暗号化し、取引先の鍵で署名して置く。こちらは CONTRL・APERAK を取引先の公開鍵あてに暗号化し、自社の鍵で署名して返す。台帳では、すべての取引先に PGP の公開鍵を必須にした。
- **復号と署名の検証は、構文の段階より前の段階**(`decryption`)。PGP の部品は `platform/file-transfer` の `PgpFiles`(暗号化 → 圧縮 → 一括署名 + 本文 + 署名だけを受け付け、署名と改竄の検知の両方が通るまで合格にしない)。b2b-gateway の `PgpDocumentCrypto` が、台帳の鍵の名前と自社の鍵の名前で使う(鍵は呼び出しのたびに読み直す)。
- **復号や署名の検証に失敗した文書**(PGP でない・自社あてでない・改竄の検知のない形式・署名がない・取引先の鍵でない署名・改竄)も、**原本(暗号文)を保管し、受け取りの記録と監査に「復号の段階で拒否」(段階 `decryption`、結果 `failure`、理由のコード)として記録する**(承認の条件 6)。交換の中身(UNB)が読めないので CONTRL は返せない。運用に知らせ(メトリクスとアラートは ⑥)、取引先には台帳の連絡先から連絡する。
- **重複の判定は、復号した交換の SHA-256 で行う**(ADR-0041 §11)。PGP の暗号文は送るたびに変わる(セッション鍵が毎回違う)ので、同じ交換の送り直しでも暗号文の SHA-256 は一致しない。監査には、原本(暗号文)の SHA-256 と、復号した交換の SHA-256 の両方を記録する。
- **取引先が署名の鍵を差し替える間は、新旧の両方の鍵の署名を受け付ける**(承認の条件 5。P10 の Webhook の鍵の差し替えと同じ考え方)。
  - 台帳の `pgp.previousPublicKeys` に、旧い公開鍵(秘密情報の名前)と、受け付ける期日(`acceptUntil`。その日の終わり UTC まで)を書く。期日を過ぎた鍵は、台帳を書き換えなくても受け付けない(取引先の鍵でない署名として拒否する)。
  - 暗号化には今の鍵だけを使う。受け取りの記録には、実際に署名した鍵の主鍵のフィンガープリントを残す(取引先が新しい鍵に移ったことを運用で確かめられる)。
  - 手順は docs/runbooks/b2b-partner-credentials.md。
- **原本を後から読めるようにする**(承認の条件 4)。暗号文の原本の復号には、受け取った当時の自社の秘密鍵が要る。

  | 案 | 内容 | 評価 |
  |---|---|---|
  | (a) 復号の鍵を保管し続ける | 取引先とやり取りする自社の秘密鍵(とパスフレーズ)を、原本の保持期間(法令で数年〜10 年程度になりうる)のあいだ、差し替えた後も保管する | 原本 1 つで読めるが、やり取りの鍵は TPA で定期的に差し替えるので、保持期間のあいだに鍵が何本も溜まる。どの原本をどの鍵で読むかの管理が要る。やり取りに使った秘密鍵を長く持つほど、漏れたときに読まれる過去の文書が増える |
  | **(b) 復号した交換を、自社の保管用の鍵で暗号化して別に保管する(採用)** | 受け取ったときに、復号した交換を自社の保管用の鍵の公開鍵で暗号化し(自社の署名つき)、原本と同じ Object Lock で別のキーに置く。送った応答も同じく置く | やり取りの鍵と保管の鍵を分けられる。**サービスが持つのは保管用の鍵の公開鍵だけ**で、読むための秘密鍵は担当部門がサービスの外(オフラインの保管や HSM)で持てる。やり取りの鍵は、保持期間と関係なく差し替えて捨てられる。原本(暗号文)は受け取ったまま残り、写しが原本と同じ交換であることは、監査の「復号した交換の SHA-256」で確かめられる |

  - (b) を採用した。写しのキーは `readable/{取引先}/received/{交換の SHA-256}.edi.pgp`・`readable/{取引先}/sent/{種類}/{SHA-256}.edi.pgp`。保管用の鍵の公開鍵は秘密情報の名前で渡す(compose は ⑥)。
  - 保管用の鍵も、保持期間のあいだ秘密鍵を保管する必要がある(1 本の鍵で済み、用途が保管だけになる)。保管用の鍵を差し替えるときは、新しい鍵で新しい写しを置く(古い写しは Object Lock で消せないので、古い鍵も保持期間のあいだ残す)。

## Alternatives Considered
- **台帳を b2b-gateway の中に持ち、file-exchange は b2b-gateway の API で台帳を読む**: 台帳は 1 か所になるが、売上ファイルの送信が b2b-gateway の稼働に同期で依存する。送信を移す(⑦)までの短い間のために API を作ることになる。不採用。
- **file-exchange と b2b-gateway がそれぞれの台帳の読み込みを持ち、ファイルだけを共有する**: 検証の規則が 2 つになり、片方だけが新しい項目を知る状態が起きる。不採用。
- **台帳を contract-check で検査する(`contracts/` に置く)**: カタログとの照合は同じようにできるが、台帳は環境ごとの設定(接続先・鍵の名前)で、契約ではない。ローカル基盤の台帳の照合は、台帳を読む部品のテストで行う。不採用。
- **鍵の期限を、SSH のサーバに問い合わせて調べる**: SSH の鍵とホスト鍵には期限の情報がない(OpenSSH の証明書を使えば期限を持てるが、取引先に求められない)。TPA の期日で監視する。不採用。
- **期限が近い鍵の送受信を止める**: 期限の前に止めると、差し替えの日程を合わせる前に送受信が止まる。アラートで知らせ、差し替えは運用の手順で行う。不採用。

## Consequences(トレードオフ)
- 台帳の形が P09 から変わった(識別子・扱う文書・鍵の期日・合意・連絡先を足し、送るデータセットは `documents` に移した)。台帳を書く手間は増えるが、TPA の項目が 1 か所にそろう。
- 鍵の期日(`validUntil`)は、運用で更新しなければ古くなる。
- **ローカル基盤の台帳の期日はコミットしない**(P12 ③ のレビュー)。固定の期日をコミットすると、日が経つだけで期限のアラートが出始め、verify の「平常時にアラートが出ないこと」と e2e が、コードを変えていないのに失敗するようになる。コミットするのはテンプレート(`infra/local/b2b/partners.template.json`。期日は `@KEYS_VALID_UNTIL@`)で、`make env` が鍵を作った日から 1 年後(`secrets/partner01-keys.valid-until`。鍵を作り直すまで変えない)を書き込んで `partners.json` を作る。CI も `make env` で作るので、いつ動かしても期限内になる。`make verify PROFILE=file` が、期日が 30 日より先であること・メトリクス・平常時にアラートが出ていないことを確かめる。
- 送信を移す(⑦)までの間は、file-exchange と b2b-gateway の両方が同じ鍵の期限のメトリクスを出す(アラートは最小値で 1 つにまとめる)。
- 台帳の連絡先には、役割の窓口を書く。個人の連絡先を書くと、台帳が個人データを持つことになる(本番の台帳の置き場の機密区分に注意する)。
