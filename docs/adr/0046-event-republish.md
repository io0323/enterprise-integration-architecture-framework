# ADR-0046: イベントの再発行
- Status: Accepted
- Date: 2026-11-05
- Framework 参照章: 6, 8, 13
- 関連: ADR-0007(Outbox)、ADR-0028(冪等消費)、ADR-0031(分析のバッチ)、#80、#116、#76
- 番号: P14 の計画で決めた番号(0044 障害注入 / 0045 SLO / 0046 イベントの再発行 / 0047 secure profile)

## Context
Outbox は発行の直後に行を消す(ADR-0007 §2)ので、次の 2 つの場合に、消えたイベントを取り戻す手段がなかった。

- **#80**: レプリケーションスロットが無効になった(`wal_status = lost`)。読まれていなかった WAL は消える。
- **#116**: batch-etl が Kafka の保持期間(14 日)を超えて止まった。トピックからイベントが消える。

どちらも注文の表には注文が残っている。P08 の後に、1 つの「イベントの再発行」の機能としてまとめて作ると決めた。

## Decision
### 1. order-service のコマンド
`order-service republish --from <時刻> --to <時刻> --reason <理由> --operator <運用者> [--run-id <ID>] [--execute]`(`make order-republish`)。

- **既定は dry-run**(対象の件数を数えるだけ)。`--execute` で書く。
- 対象は注文の時刻(`ordered_at`)が範囲に入る注文。100 件ごとに 1 つのトランザクションで Outbox に書き、発行はふだんの経路(Debezium)で行う。
- 途中で失敗しても、書いた分は確定している。**同じ範囲でやり直してよい**(§3)。
- 監査に `order.republish` を 1 件記録する。範囲・件数・理由のハッシュと、実行の ID を残す。

### 2. 作り直せる内容(途中の遷移は戻らない)
| イベント | 内容 |
|---|---|
| `sales.order.created.v1` | 作成の時点の内容。状態は `PLACED`。明細と金額は変わらないので、今の注文から作れる |
| `sales.order.status-changed.v1` | **今の状態への遷移を 1 件だけ、今の版で**(状態が `PLACED` のままなら出さない)。`previousStatus` は `PLACED`、`changedAt` は最後の更新の時刻 |
| `sales.order.cancelled.v1` | 取り消されていれば。理由は Saga の補償の理由(なければ `UNKNOWN`) |

- **途中の遷移(`CONFIRMED` など)は戻らない。** 注文の表には今の状態しかないため。`previousStatus` と遷移の回数は実際と違うことがある。
- 分析の週次の照合は今の状態のハッシュで比べるので、途中の遷移がなくても一致する(`EventRepublishE2E`。再発行の前は DRIFT、後は MATCH)。

### 3. 重複の扱い
`ce_id` は新しくなる(元の `ce_id` は UUIDv7 で、注文から作り直せない)。**受信側は業務のキーで重複を除く。**

- `INT-SALES-002` の購読者は batch-etl だけで、業務のキーで冪等にしている(ADR-0031 §4)。
  - `raw.order_placed`: 注文 ID。`raw.order_status_change`: 注文 ID と版。`raw.order_cancelled`: 注文 ID。
- 新しい購読者を足すときは、業務のキーで重複を除く必要がある。

### 4. 再発行の目印
再発行したイベントにはヘッダを付け、分析の側で元のイベントと区別できるようにする(P06 ⑥ の reconcile の tombstone の目印と同じ考え方)。

| ヘッダ | 値 |
|---|---|
| `eiaf.republished` | `true` |
| `eiaf.republish.reason` | 理由(例 `slot-lost`・`retention-exceeded`) |
| `eiaf.republish.run-id` | 実行の ID |

- Outbox の表に列を足し(`republished`・`republish_reason`・`republish_run_id`)、コネクタ `order-outbox` がヘッダにする。ほかのサービスのコネクタは変えない。
- ふつうのイベントでは列は NULL で、**ヘッダの値は null になる**。
- 理由・運用者・実行の ID は決まった文字だけにする(業務のデータを入れない)。

### 5. Saga のコマンドは再発行しない
Saga のコマンド(`inventory.stock.cmd-*` など)も同じ Outbox を通るが、再発行するのは注文のイベントだけにする。送り直すと、終わった Saga の段が動く恐れがあるため。

- スロットがない間に書いたコマンドは届かない。その注文は段の期限で補償に進み、`CANCELLED`(`TIMED_OUT`)になる(`EventRepublishE2E` で確かめた)。
- 補償のコマンドは、返信が来るまで Orchestrator が送り直す(ADR-0029)ので、発行が戻れば届く。
- 再発行は Saga を動かし直さない。**イベントが戻っても、取り消された注文は取り消されたまま。**

## Alternatives Considered
- **#76(Outbox の行を保持する方式)で、そのまま送り直す**: より忠実な再現になる。行が残っていれば、元と同じ `ce_id` と途中の遷移を含めてそのまま送り直せる。**#80(スロットの失効。数日の範囲)はほぼ覆えるが、#116(Kafka の保持期間の超過)は、Outbox の保持期間をそれより長くしない限り覆えない。** 表の肥大と保持の運用(日ごとのパーティションと DROP)が増え、最後のフェーズで入れるには範囲が大きいので、今回は入れない。忠実さが必要になったら #76 で扱う。
- **状態の履歴の表を足す**: これ以降の注文の途中の遷移を残せるが、すでにある注文には効かず、書き込みの処理が増える。不採用。
- **分析向けの抽出の API を足す**(#116 の案 2): 分析だけの解決になり、#80 を覆えない。不採用。

## Consequences(トレードオフ)
- 再発行したイベントは、途中の遷移を持たない。分析の遷移の履歴には穴が残る。
- 範囲を広く取ると、届いていたイベントも再発行する。購読者の冪等に頼る。
- 範囲は受け付けの時刻で決める。**範囲より前に受け付けた注文の遷移が消えていても、その注文は対象にならない。** 始まりは、受け付けから完了までの時間の分だけ広めに取る(Runbook)。
- スロットの失効で失った Saga のコマンドで、注文が取り消されることがある(§5)。
- Outbox の表の列が全サービスで増える(使うのは order だけ)。
