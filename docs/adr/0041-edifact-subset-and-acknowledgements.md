# ADR-0041: EDIFACT のサブセットの仕様・構文と文字セット・受領の応答(CONTRL と APERAK)
- Status: Accepted
- Date: 2026-10-30
- Framework 参照章: 11.1, 11.2, 11.3, 15, 16
- 関連: ADR-0008(B2B のプロトコルは SFTP だけ。受領の応答は CONTRL 相当)、ADR-0040(B2B Gateway。P12 ③ で書く)
- 番号: P12 の計画で予約した番号(0040 B2B Gateway / 0041 EDIFACT)。0040 は ③ で書くため、一時的に番号が飛ぶ

## Context
P12(B2B / EDI Gateway。#15)では、取引先が SFTP で置く UN/EDIFACT の受注の文書(ORDERS)を b2b-gateway が受け取り、構文 → スキーマ → 業務の 3 段階で検査して、結果を取引先に返す(Framework 11.1)。ROADMAP は「CONTRL 相当の受領応答」と書いている。

決める必要があるのは次の点。

1. どの標準の、どの範囲を扱うか(サブセット)と、その仕様をどこに、どの形で置くか
2. 構文(ISO 9735)の版と、区切り文字の指定(UNA)の扱い
3. 文字セット(UNOA・UNOB・UNOC など)の扱い
4. 3 段階の検査の分け方と、エラーの表し方(位置とコード)
5. 応答の種類(CONTRL だけか、APERAK も使うか)と、返す条件
6. 試験の交換の扱い

標準の値は推測で書かない(CLAUDE.md §2 の考え方)。UN/CEFACT の一次の資料(service.unece.org)は、2026-10-30 の時点で自動の取得を拒否した(HTTP 403)。そこで、ディレクトリの写しと解説の資料で確かめ、確かめられなかった値は仕様に使わない形にした(§8)。

## Decision

### 1. 範囲: ORDERS(D.96A)のサブセットと、CONTRL・APERAK
- 受け取るのは **ORDERS の D.96A のサブセット** だけ(`contracts/files/edi/edifact-orders.v1.yaml`)。1 つのメッセージが 1 つの注文。
  - 使うセグメント: BGM・DTM(注文日 137・納期 2)・NAD(買い手 BY・売り手 SU・届け先 DP。GLN で表す)・CUX・LIN(GTIN)・PIA(取引先の商品コード。任意)・QTY・PRI・UNS・CNT(任意)。
  - 個人の住所や氏名は含めない(届け先は GLN で表し、社内の住所への対応は取引先ごとの対応表で行う。ADR-0040)。
  - 注文の変更・取消(ORDCHG・BGM の 1225 が 9 以外)、注文の応答(ORDRSP)、出荷の案内(DESADV)は範囲外。
- 返すのは **CONTRL**(構文の版 3 のサービスのメッセージ。`edifact-contrl.v1.yaml`)と **APERAK**(D.96A。`edifact-aperak.v1.yaml`)。
- 機能グループ(UNG / UNE)は使わない。UNG があれば構文の段階のエラー(0085 = 15)にする。

### 2. 構文: 版 3 だけ。UNA を必須にする
- **構文の版は 3 だけ** を受け付ける(UNB の 0002)。ほかの版は構文の段階のエラー(0085 = 2)。
  - P12 の計画では版 3 と 4 を挙げたが、①で版 3 だけにした。D.96A の ORDERS と CONTRL(D:3)は版 3 の世界で、版 4 は繰り返しの区切り文字・小数点の扱い・UNB の日付の長さ(CCYYMMDD)・使える文字セット(UNOY など)が違う。版 4 が必要な取引先が出たら、新しい版の仕様で足す(§7)。
- **UNA(区切り文字の指定)を必須にする**。UNA がない交換は、構文の段階のエラー(0013 = UNA、0085 = 13)にする。
  - 理由 1: UNA がないときの既定の小数点は、**構文の版 1〜3 ではカンマ**で、よく使われる UNA の例(`UNA:+.? '`)の点と違う。取引先とこちらで取り違えると、単価の桁を誤って読む(§8 の資料)。
  - 理由 2: UNOB の、UNA がないときの既定の区切り文字(制御文字)を確かめられる資料が見つからなかった。
  - UNA の 6 文字は、順に「構成要素の区切り・データ要素の区切り・小数点・解放文字・予約(版 3 では空白)・セグメントの終端」。予約の位置が空白でなければ構文の段階のエラー(0085 = 20)。
  - 応答を返すために、UNA がない交換でも UNB の送り手・管理番号は読もうとする(UNB の中は区切り文字だけで読める)。読めなければ応答を返さず、運用にだけ知らせる。
    - このときは、よく使われる区切り文字 `:+.? '` で読む(`ServiceCharacters.FALLBACK`)。宛先を読むためだけで、交換は UNA の誤りとして拒否する(P12 ②a)。
  - **UNA の区切り文字も、UNB の文字セットに入る文字でなければならない**(予約の空白を除く)。入らなければ 0085 = 20。例えば `|` と `#` は UNOA・UNOB に入らない(ISO 646 で国ごとに割り当てが変わる位置)ので、UNOC の交換でだけ使える(P12 ②a)。
- **解放文字**(既定の `?`)の直後の 1 文字は、区切り文字・終端・解放文字であっても値の文字として読む。解放文字が値の最後(終端の直前)にあるのは構文の段階のエラー(0085 = 20)。
- **小数点** は UNA で指定した文字だけを受け付ける(版 3 では、指定と違う小数点は 0085 = 19)。小数点の前に数字がない値(`.5`)は 0085 = 38。数値の長さ(`n..15` など)には、小数点と符号を数えない(ISO 9735)。
- **改行**: セグメントの終端の直後の CR・LF だけは読み飛ばす(取引先の製品が付けることが多い)。それ以外の位置の制御文字は、文字セットの外の文字(0085 = 21)。

### 3. 文字セット: UNOA・UNOB・UNOC を受け付け、受け取った文字セットで返す
- 受け付けるのは、構文の版 3 の **UNOA**(UN/ECE level A。ISO 646 の基本の表から英小文字などを除いた集合)、**UNOB**(level B。ISO 646 の基本の表)、**UNOC**(level C。ISO/IEC 8859-1)。
  - UNOY(ISO 10646。版 4 の文字セット)と、UNOD〜UNOF(ISO 8859-2・-5・-7)は範囲外(0085 = 2 ではなく、UNB の 0001 の値の誤り 0085 = 12)。
  - バイト列から文字への変換は、UNOC では 1 バイトを 1 文字に対応させる(ISO 8859-1)。UNOA・UNOB は 7 ビットの範囲だけ。集合の外の文字は、構文の段階のエラー(0085 = 21)。
  - **各集合に含める文字**(P12 ②a。`CharacterSet` と単体テストで固定)
    | 文字セット | 含める文字 |
    |---|---|
    | UNOA | 英大文字・数字・空白と、ISO 646 で割り当てが変わらない位置の記号 `. , - ( ) / = ' + : ? ! " % & * ; < > _` |
    | UNOB | UNOA に英小文字を足したもの |
    | UNOC | ISO 8859-1 の図形文字(0x20〜0x7E と 0xA0〜0xFF) |

    - 除く文字: 制御文字(CR・LF を含む)、ISO 646 で国や用途で割り当てが変わる位置の `# $ @ [ \ ] ^ ` { | } ~`(UNOA・UNOB)、英小文字(UNOA)。
    - `_`(下線)は、§8 で確かめた定義(ISO 646 の基本の表から英小文字と、割り当てが変わる位置を除く)に従うと UNOA に入る。よく出回っている UNOA の文字の一覧には `_` がないものがあるが、受け取る側では定義に従って受け付ける。こちらが足す文言(業務の規則の固定の文言)には `_` を使わない(EDI の仕様のスキーマの `text` の形)。
  - **UNB の 0001 が知らない値のとき**は、交換を拒否し(0085 = 12)、CONTRL は **UNOC** で返す。交換は ISO 8859-1 として読んでいるので、受け取った識別子は UNOC で必ず表せる(P12 ②a)。
- **応答は、受け取った交換と同じ文字セット(UNB の 0001)と構文の版で返す**。応答には取引先の識別子・管理番号・注文番号をそのまま写すので、受け取った文字セットで表せることが保証される。こちらが足す文言(業務の規則の固定の文言)は UNOA で表せる文字(英大文字・数字・記号)だけにする(EDI の仕様のスキーマの `text` の形)。

### 4. 3 段階の検査と、エラーの表し方
| 段階 | 検査すること | 返し方 |
|---|---|---|
| 1. 構文 | UNA・UNB・UNZ・UNH・UNT の有無と形、区切り文字・解放文字・小数点、文字セット、UNB の送り手と受け手(取引先の台帳と自社の識別子)、UNZ / UNT の件数(0036・0074)と管理番号の一致(0020・0062)、交換の管理番号の重複(ADR-0040) | CONTRL。交換の誤りは UCI(0083 = 4)、メッセージの枠の誤りは UCM(0083 = 4) |
| 2. スキーマ | サブセットの仕様に従った、セグメントの並び・回数・修飾子ごとの回数(グループを含む)、データ要素の状態(M・C・X)・形式(a・n・an と長さ)・コード値・日付と時刻 | CONTRL。メッセージを UCM(0083 = 4)で拒否し、位置を UCS(セグメント)と UCD(データ要素)で示す |
| 3. 業務 | 取引先ごとのコードの対応表・合意した通貨・日付の整合・注文番号の重複・件数(CNT)・数量と単価(仕様の `businessRules`) | APERAK(4343 = RE)。理由ごとに ERC と FTX |

- 1 つの交換の中のメッセージは、それぞれ独立に検査する。段階 1・2 で拒否したメッセージだけを UCM で 4 にし、ほかのメッセージは UCM で 7 にして段階 3 に進める。交換そのものの誤り(UNB・UNZ・UNA)は、UCI で 4 にして、中のメッセージは検査しない(UCM を付けない)。
- **位置の数え方**: UCS の 0096 は、UNH を 1 として数えたメッセージの中のセグメントの位置。UCD の 0098 は、セグメントのタグの次のデータ要素を 1 として数えた位置、0104 は複合データ要素の中の構成要素の位置(1 から)。
- **使う 0085 のコード**(CONTRL の仕様の codes に並べた値だけ)

  | 0085 | 使う場面 |
  |---|---|
  | 2 | 構文の版が 3 でない |
  | 7 | UNB の受け手が自社でない |
  | 12 | 値がサブセットのコード値にない・日付や時刻として正しくない |
  | 13 | 必須のセグメント・データ要素がない(UNA を含む) |
  | 15 | このサブセットで使わない位置に値がある(X)・並びの外のセグメント・UNG |
  | 16 | データ要素・構成要素の数が定義より多い |
  | 18 | ほかのどれにも当たらない誤り(使うときは、どの規則にも当たらなかったことをログに残す) |
  | 19 / 38 | 小数点の誤り / 小数点の前に数字がない |
  | 20 | 区切り文字の誤り(UNA の予約の位置・解放文字の位置) |
  | 21 | 文字セットの外の文字 |
  | 23 | UNB の送り手が取引先の台帳にない(その SFTP の場所の取引先と一致しない場合を含む) |
  | 26 | 交換の管理番号の使い回し(同じ番号で中身が違う。ADR-0040) |
  | 28 | UNB と UNZ の 0020、UNH と UNT の 0062 が一致しない |
  | 29 | UNZ の 0036・UNT の 0074 が実際の数と一致しない |
  | 32 | 交換にメッセージがない |
  | 33 | メッセージの外(UNB と UNH の間、UNT と次の UNH の間)にセグメントがある |
  | 35 / 36 | セグメントの回数 / グループの回数が上限を超える |
  | 37 | 文字の種類が形式と違う(n に英字など) |
  | 39 / 40 | データ要素が長すぎる / 短すぎる(固定長) |

### 5. 応答の方針
- **CONTRL は、受け取った交換ごとに必ず返す**(受け付けた交換にも、UCI の 0083 = 7 で返す)。UNB の 0031(応答の要求)の値によらない。返さない取引先を作る場合は、取引先の台帳(TPA)に設定を足す(③)。Framework 11.3 のアンチパターン「997/MDN 未確認運用」を、こちらから作らないため。
- **APERAK** は、受注の文書のメッセージごとに返す。
  - 業務の段階で拒否したら **必ず返す**(4343 = RE。理由ごとに SG3 の ERC と FTX)。
  - **業務の受け付けに成功したときに返すか(肯定の応答。4343 = AP)は、取引先ごとに TPA で選ぶ**(取引先の台帳の項目。③)。
    - **肯定の応答は、社内の受注のシステム(order の API)が受け付けた後に返す**(⑤。P12 ②b)。業務の検査に合格した時点で AP を返すと、その後に order が受け付けなかったとき、同じ注文に AP と RE の両方を返すことになるため。業務の段階で拒否した注文の RE は、検査の直後に返す。
    - 例外は試験の交換(§6)。社内に取り込まないので、取引先が肯定の応答を選んでいれば、検査の直後に AP を返す。
  - **返すまでの期限は TPA の項目にする**(③)。期限に近づいた送信待ちはアラートにし、promtool のテストを付ける(⑤・⑥)。
  - 業務の検査に合格した後、社内の受注のシステム(order の API)が受け付けなかったときも、APERAK(RE)で返す。理由は APERAK の仕様の `errorTexts` の固定の文言(`APR901`)だけで、order が返した理由は入れない(ADR-0040)。
- **APERAK の BGM の 1001 は `23`(Status information。関連するメッセージの状態の情報)** にする。D.96A の 1001 のコード表に、APERAK の専用のコードは見当たらなかった。取引先の製品が別のコードを求めたら、取引先の台帳ではなく、新しい版の仕様で扱う(1 つの版の中で値を取引先ごとに変えない)。
- 注文の参照は SG1 の RFF の **CO(Buyers order number)** に、受け取った BGM の 1004(取引先の注文番号)を入れる。ERC の 3055 は **ZZZ(Mutually defined)** で、9321 は仕様の規則のコード(an..8)。
- **取引先に返すエラーに、社内の情報を入れない**: CONTRL は標準のコードと位置だけ、APERAK は仕様に書いた固定のコードと文言だけで組み立てる。例外のメッセージ・スタックトレース・社内の ID・order の応答の本文は入れない。組み立ての側(②)は、文言を仕様からしか取れない形にし、単体テストで確かめる。
- 応答のファイル名と置き場所(取引先の SFTP のディレクトリ)は、取引先の台帳で決める(③・⑦)。売上ファイルの送信と同じ送信の仕組みで送る(⑦。P12 の承認の条件 3)。

### 6. 試験の交換(UNB の 0035 = 1)
- 試験の交換も、3 段階の検査と応答(CONTRL・APERAK)は本番と同じに行い、応答の UNB にも 0035 = 1 を付ける。**社内には取り込まない**(order の API を呼ばない)。原本の保管と監査の記録は行う(ADR-0040)。
- 取引先が試験の交換を送れる期間(接続の試験の間だけなど)は、取引先の台帳で決める(③)。

### 7. 仕様を単一の真実にする
- 仕様は `contracts/files/edi/{name}.v{n}.yaml`(MODULE_DESIGN §3.1 の置き場所)、形は `contracts/files/edi-spec.v1.schema.json`。サービスセグメント(UNB・UNH・UNT・UNZ)も含めて、使うセグメント・データ要素・コード値・並びと回数・業務の規則(コードと固定の文言)を書く。
  - 状態(M・C・X)は、標準より厳しくだけする(標準の C を M か X にする)。
  - データ要素は位置で読むので、使わない位置も、最後に使う位置までは X で書く。
  - コードの名前は、標準のコード表の表記(英語)。
- b2b-gateway は仕様をリソースとして読み込み、スキーマの段階の検査と応答の組み立てに使う(②)。業務の規則のコードと文言も仕様から取り、論理だけを b2b-gateway に書く。
- **contract-check の規則**(`tools/contract-check/README.md`)
  - `CC-EDI-001`: 仕様が EDI の仕様のスキーマに適合する(inbound には応答の仕様と業務の規則が必須)。
  - `CC-EDI-002`: 仕様の中の参照が食い違わない(ファイル名と name・version、並びのセグメントの定義、グループの最初は M のセグメント、修飾子は最初のデータ要素の codes の値、UNH の S009 と `message`、UNB の S001 と `syntax`、コード値が format に収まる、応答の仕様は outbound、業務の規則のコードの一意)。
  - `CC-EDI-003`: 仕様は `style: edi` のカタログに登録され、`style: edi` のカタログの contract は EDI の仕様。
  - `CC-COMPAT-005`: 出した版の中身を変えない(説明の文 `description` と名前 `name` だけは直してよい)。取引先は出した版に合わせて EDI の製品を設定するため。変更は新しい版のファイルで足し、取引先ごとの切り替えは取引先の台帳で行う。設計中(design)の連携だけが使う仕様の変更は、ほかの契約と同じく許す(ADR-0013 §7)。
- **カタログの単位は「文書の種類 × 向き」**: INT-B2B-001(ORDERS の受信)、INT-B2B-002(CONTRL の送信)、INT-B2B-003(APERAK の送信)。取引先ごとの参加は、カタログではなく取引先の台帳(TPA)で持つ。台帳が扱う文書の種類はカタログの ID で書き、カタログにあること・EDI かファイルの連携であることを、台帳を読む部品(`platform/trading-partner`)のテストで確かめる(ADR-0040 §2)。

### 8. 確かめた資料と、確かめられなかった値の扱い
- **確かめた資料**(2026-10-30。一次の資料 service.unece.org は HTTP 403 で取得できなかったため、写しと解説)
  - Stylus Studio の UN/EDIFACT ディレクトリの写し(<https://www.stylusstudio.com/edifact/>): 構文の版 3 のサービスセグメント(UNB・UNH・UNT・UNZ・UCI・UCM・UCS・UCD)と、0001・0013・0031・0035・0083・0085 のコード表。D.96A のセグメント(BGM・DTM・NAD・CUX・LIN・PIA・QTY・PRI・CNT・RFF・ERC・FTX)と、1001・1225・2005・2379・3035・3055・4343・4347・4451・5125・6063・6069・6343・6347・7143 のコード表。CONTRL のメッセージの構成。
  - EDIFACTORY(<https://www.edifactory.de/edifact/directory/D96A/message/ORDERS>・`.../APERAK`): ORDERS と APERAK の D.96A のセグメントの表(グループの番号 SG2・SG7・SG25・SG28)。
  - Stedi(<https://stedi.com/edi/edifact/D04A/elements/0081>)と GEFEG のコード表: UNS の 0081 の S(Detail/summary section separation)。
  - Wikipedia の EDIFACT の記事(ISO 9735 を出典とする): UNA がないときの既定の区切り文字と、版 1〜3 の既定の小数点がカンマであること。
- **確かめられなかった値と、その扱い**
  | 値 | 扱い |
  |---|---|
  | UNA がないときの UNOB の既定の区切り文字(制御文字) | UNA を必須にした(§2) |
  | 1153 の ON(注文番号) | 確かめた CO(Buyers order number)を使う |
  | 6411 の PCE(個数) | 数量の単位は使わない(X) |
  | APERAK の BGM の 1001 の専用のコード | D.96A の表にある 23(Status information)を使う(§5) |
  | UNB の 0007(識別の機関)のコード値 | 仕様では値を固定せず、取引先の台帳の値と一致することを検査する |
  | 9321 のコード表の有無 | ERC の構成(9321 は an..8)だけを使い、値は仕様の規則のコード、3055 = ZZZ |
- 一次の資料(UN/CEFACT・ISO 9735)を取得できる環境で、仕様の値を照合し直すことを、P12 の後の作業として残す(この ADR の改訂で記録する)。

### 9. ROADMAP の読み替え
- ROADMAP P12 の「CONTRL 相当の受領応答」は、**構文とスキーマの段階は CONTRL、業務の段階は APERAK** と読み替える(P12 の計画の判断 2。案 B)。EDIFACT の標準では、CONTRL は構文とサービスの報告で、業務の拒否は APERAK が担う。取引先の EDI の製品が、そのまま解釈できる。
- DoD の「構文・スキーマ・業務のそれぞれのエラーで、正しいエラー応答と運用通知が出る」は、段階 1・2 の CONTRL と段階 3 の APERAK で確かめる(⑧)。肯定の APERAK も E2E で確かめる(承認の条件 1)。

### 10. 解析と検査の実装(P12 ②a)
- **字句の解析・検査・CONTRL の組み立て・書き出しは、b2b-gateway の domain(commonMain)に自前で書く**(`edifact`・`validation`・`ack` のパッケージ)。仕様のモデル(`spec`)も domain に置き、契約の YAML から作るのは adapters(`YamlEdiSpecs`。契約のファイルをビルドでリソースに写し、テストで契約と同じことを確かめる)。
- **交換は ISO 8859-1 として 1 バイトを 1 文字に読んでから区切る**。UNOA・UNOB・UNOC はどれも 1 バイトが 1 文字で、区切り文字は ASCII なので、文字セットを読む前に区切ってよい。文字セットの集合の検査は、UNB を読んだ後に値ごとに行う。
- **枠の誤りの扱い**
  - 交換の枠: UNA の誤り、UNB の誤り(版・文字セット・データ要素)、UNG、UNZ がない(書きかけ)、UNZ のデータ要素・件数・管理番号の誤り、メッセージの外のセグメント(0085 = 33)、メッセージがない、メッセージが多すぎる(0085 = 35 / UNH)。UCI で拒否し、UCI の 0085 には最初の 1 つだけを入れる(UCI は 0085 を 1 つしか持てない)。
  - メッセージの枠: UNH のデータ要素(メッセージの型が仕様と違うなど)、UNT がない(次の UNH か UNZ の前までを、そのメッセージとする)、UNT のデータ要素・参照番号・件数。UCM で拒否し、最初の 1 つを UCM の 0085 に入れる。
  - メッセージの中身: データ要素と並びの誤りを位置ごとにまとめ、UCS(セグメントの誤り。1 つ)と UCD(データ要素の誤り)で返す。並びのどこにも当てはまらないセグメントで、並びの検査をやめる(以降の位置は数えられないため)。報告は CONTRL の仕様の上限(UCS 99・UCD 99)まで。
- **自分が出す CONTRL が、自分の CONTRL の仕様に従うこと**を、adapters のテストで確かめる(組み立てた CONTRL を、同じ検査で CONTRL の仕様に照らす)。取引先に返す CONTRL に、標準のコードと位置と受け取った識別子のほかの値がないことも、同じテストで確かめる(§5)。

### 11. 取引先の識別と、交換の重複(EDI の層での冪等。P12 ②b)
- **取引先は、ファイルを受け取った SFTP の場所で決まる**(④)。受け取りのユースケース(`ReceiveInterchangeUseCase`)には取引先の ID を渡し、台帳の合意(`PartnerAgreement`)と照らし合わせる。
  - UNB の送り手(S002 の識別子と識別の機関)が、その取引先の台帳の識別子と違えば 0085 = 23(Unknown Interchange sender)。ほかの取引先の識別子を名乗った交換を、その取引先の注文として取り込まないため。
  - UNB の受け手(S003)が自社の識別子と違えば 0085 = 7。
  - 取引先の ID が台帳にないのは、置き場所と台帳の設定の食い違い(取引先の誤りではない)なので、応答を返さずに設定の誤りにする(`UnknownPartner`)。
- **重複の判定のキーは、取引先の ID・UNB の送り手・受け手・交換の管理番号(0020)の組**。**復号した交換の SHA-256** と、前に受け取った交換の記録(`ReceivedInterchanges`。初めての受け取りの記録)を比べる。PGP の暗号文は送るたびに変わるので、暗号文の SHA-256 では比べない(ADR-0040 §8。P12 ④a)。
  - 同じ SHA-256 → 送り直し。取り込まず、業務の検査も応答の組み立てもしないで、**前に返した CONTRL と APERAK をそのまま返し直す**(前の記録の応答と同じ原本(暗号文)を、もう一度送信待ちにする。応答の管理番号も新しく振らない)。取引先が応答を受け取れずに送り直した場合に、同じ応答が届く。
  - 違う SHA-256 → 管理番号の使い回し。交換を拒否する(0085 = 26、0013 = UNB、S011 = 5)。
  - UNB を読めない交換は、キーが作れないので重複の判定をしない(応答も返さない。§2)。
- **交換の拒否の理由が重なったときは、使い回し(26)→ 構文とスキーマの段階の交換の誤り → 送り手(23)→ 受け手(7)の順に、最初の 1 つを UCI に入れる**(UCI は 0085 を 1 つしか持てない)。使い回しを先にするのは、前の交換と中身が違うこと自体が、取引先がまず直すべきことだから。
- **業務の段階の注文番号の重複(ORD007)**は、交換の重複とは別に扱う。同じ取引先から前に受け付けた注文番号(`ReceivedOrders`)と、同じ交換の中で先に出てきた注文番号を、重複にする。
- 対応表(`CodeMappings`)は、交換の中の注文に出てくるコードをまとめて 1 回引く。引いた結果(`CodeResolution`)は、社内への取り込み(⑤)でも使う。

## Alternatives Considered
- **3 段階とも CONTRL で返し、業務のエラーは独自のコードにする**: ROADMAP の字面どおりだが、CONTRL の 0085 は構文の誤りのコードで、業務の理由を表せない。取引先の製品が解釈できない独自の使い方になる。不採用(計画の判断 2)。
- **構文の版 4 も受け付ける**: 取引先の幅は広がるが、区切り文字・小数点・日付・文字セットの規則が版ごとに分かれ、検査と応答の組み立てが倍になる。D.96A の取引先が版 4 を求める根拠もない。必要になったら新しい版の仕様で足す。不採用。
- **UNA を任意にし、ないときは既定の区切り文字で読む**: 標準どおりだが、既定の小数点(カンマ)の取り違えと、確かめられない UNOB の既定値の問題が残る。TPA で UNA を付けることを合意するほうが安全。不採用。
- **仕様を標準の形式(UN/CEFACT の XML のディレクトリや、EDI の製品の独自の形式)で持つ**: 道具は揃うが、サブセットの絞り込み(M・C・X・修飾子ごとの回数)と業務の規則を同じ場所に書けず、contract-check で検査しにくい。JSON Schema で形を決めた YAML なら、ほかの契約と同じ仕組み(形・参照・互換性)で扱える。不採用。
- **解析に既存の JVM の EDI のライブラリを使う**: 検査と解析を b2b-gateway の domain(KMP の commonMain。ADR-0004)に置くと、JVM のライブラリは使えない。サブセットは小さく、区切り文字・解放文字・文字セットの規則は §2・§3 で閉じている。不採用(P12 ②a で、字句の解析 `EdifactLexer`・検査・書き出しを domain に自前で書いた。§10)。

## Consequences(トレードオフ)
- 取引先は、UNA を付けること・構文の版 3・UNOA / UNOB / UNOC・機能グループを使わないことを、TPA で合意する必要がある。合わない取引先には、新しい版の仕様か、取引先の側の設定の変更が要る。
- 出した版の仕様は変えられない(`CC-COMPAT-005`)。小さな直し(コード値の追加など)も新しい版のファイルになり、取引先ごとに切り替える手間がかかる。その代わり、取引先が知らないうちに検査の規則が変わることはない。
- 一次の資料で照合できていない値が残る(§8)。照合できるまでは、仕様の値の出典は写しと解説の資料になる。
- サービスセグメントの定義は、仕様ごとに書く(CONTRL と APERAK で同じ定義が並ぶ)。仕様が単独で読めることを優先した。
