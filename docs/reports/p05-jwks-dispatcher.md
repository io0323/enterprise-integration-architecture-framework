# P05 ⑨: JWKS の取得を待つ検証の dispatcher の計測

ADR-0019 の Consequences で P05 に持ち越した判断(`JwtVerifier.verify` を共有の `Dispatchers.IO` で動かしてよいか)の根拠。結論と設計は ADR-0019 §3(2026-10-02 の改訂)。

## 結論
- **共有の `Dispatchers.IO` のままでは、IdP が遅いときに、DB の処理まで IdP の待ち時間だけ待たされる**(方式 A)。
  - 同時の検証が IO の上限(64)を超えると、DB の処理の待ちが、IdP の応答の時間(1.5 秒・2 秒)とほぼ同じになった。
  - 64 未満(50)でも、DB の処理の待ちは p50 でおよそ 100 ms に伸びた(ふだんは 30 ms 前後)。
- **`Dispatchers.IO.limitedParallelism(16)`(方式 B)を採用した。**
  - 同じ状況で、DB の処理の待ちは、ふだんと変わらなかった。
  - キャッシュがあるときの検証の速さも、方式 A と同じだった。
- **仮想スレッド(方式 D)も、DB の処理を待たせなかった。** JWKS の取得の経路で、ピン留めも起きなかった(下)。B を選んだ理由は「方式の比較」。

## 計測の方法
- 計測のコード: `platform/security/src/measurement/kotlin/io/eia/platform/security/jwt/JwksDispatcherMeasurement.kt`
- 実行(手動。`./gradlew build` と CI には含めない。Issue #46 の教訓): `./gradlew :platform:security:measureJwksDispatcher`
  - 条件は `-Pjwks.verifications=200 -Pjwks.dbTasks=100 -Pjwks.dbWorkMs=20 -Pjwks.repeat=3` で変えられる(値は既定値)。
  - 1 回の実行は 8〜10 分(キャッシュの期限切れを待つため)。
- 手順(状況 × 方式 × 回ごとに、新しい `JwtVerifier` と JWKS のサーバで行う)
  1. 応答を遅らせられる JWKS のサーバ(JDK の `HttpServer`)を立てる。JWKS の取得は、本番と同じ Nimbus の `DefaultResourceRetriever`(`HttpURLConnection`)で、実際の HTTP で行う。
  2. 1 回検証して、JWKS をキャッシュに入れる。
  3. 期限切れの状況では、キャッシュの期限(計測のために 20 秒にした)が過ぎるまで、何も送らずに待つ。そのほかの設定は ADR-0019 §3 の既定値(取り直しの待ち 15 秒・接続と読み取りのタイムアウト 2 秒など)。
  4. IdP の遅延を設定し、検証を N 件、同時に始める。各方式の dispatcher で `verifyBlocking` を呼ぶ。
  5. 50 ms 後に、DB の処理を模した M 件を同時に始める。各 20 ms の `Thread.sleep` を `Dispatchers.IO` で行い、始めてから終わるまでの時間を測る。order-service の Exposed は `Dispatchers.IO` で動く(`services/order/adapters/.../Jdbc.kt`)。
- 比べた方式
  - **A**: 共有の `Dispatchers.IO`(変更の前)
  - **B**: `Dispatchers.IO.limitedParallelism(16)`。`Dispatchers.IO` の view で、view のスレッドは共有の上限(64)の外で増える
  - **C**: JWKS の取得をリクエストの経路から外し、裏で取り直す方式。変更が大きいので、計測はせずに比べた(「方式の比較」)
  - **D**: 仮想スレッド(`Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher()`)
- 環境
  - マシン: MacBook Pro、Apple M3(8 コア)、メモリ 8 GiB、macOS 26.3.1
  - JDK: Temurin 21.0.7+6(aarch64)
  - kotlinx.coroutines 1.11.0、Nimbus JOSE+JWT 10.10
  - 計測の間、ほかの Gradle のビルドと Docker のコンテナは止めた。

### 読み方
- **期限切れの後の最初の要求が JWKS を取り直し、ほかの要求はその取得を待つ。** Nimbus のキャッシュのロックで待ち、待つ時間の上限は `refreshTimeout`。
  - JWKS の取得は、どの回も 1 回だけだった(同時の取り直しはまとめられる)。
  - IdP が応答しないときは、読み取りのタイムアウト(2 秒)の後に `outageTolerance` で最後の JWKS を使い、すべて成功した。
- **方式 A では、待っている検証が IO のスレッドを 1 本ずつ塞ぐ。**
  - 同時の検証が 64 以上だと、IO のスレッドが全部塞がり、DB の処理は IdP の待ちが終わるまで始まらない。
  - 64 未満でも、残りのスレッドで DB の処理を回すので、待ちが伸びる。
  - order-service の DB の処理は `Dispatchers.IO` で動くので、IdP の遅れが、JWT と関係のない DB の処理の遅れになる。
- **方式 B と D では、検証は DB の処理とは別のスレッドで待つ。**
  - IdP の待ちは検証の時間には出る(どの方式でも同じ)が、DB の処理には出ない。
  - B で、16 件より多くの検証が来た分は、スレッドを持たずにコルーチンの列で待つ。ロックを待つ検証と同じく、取得の終わりを待つことに変わりはない。
- **キャッシュが有効なとき、検証は CPU だけの処理。** B の上限(16)は CPU の数(8)より多く、検証の速さは A と変わらなかった。

## 仮想スレッド(方式 D)のピン留め
- JDK 21 では、仮想スレッドが `synchronized` の中でブロックすると、実際のスレッド(carrier)を手放せない(ピン留め)。
- 計測のタスクは `-Djdk.tracePinnedThreads=full` で実行した。ピン留めが起きると、JDK がスタックトレース(`<== monitors:N`)を出す。
- **結果: JWKS の取得の経路(D の全回)では、スタックトレースは 0 件だった。**
  - JWKS を取得する仮想スレッド(`HttpURLConnection` の接続と読み取り)でも、ロックで待つ仮想スレッドでも、出なかった。
  - Nimbus のキャッシュは `ReentrantLock` で待つ。JDK 21 の `HttpURLConnection` は、内部のロックが `ReentrantLock` になっている。
- **検出が働いていることの対照**: 計測の最後に、仮想スレッドで `synchronized` の中で `sleep` させた。スタックトレースが 1 件出た(`reason:MONITOR`、`JwksDispatcherMeasurement.kt` の `pinningControl`)。
- この結果は、この版の組み合わせ(JDK 21.0.7・Nimbus 10.10)でのもの。経路に `synchronized` の中で待つコードが入れば、JDK 21 ではまたピン留めが起こりうる。JDK 24 以降(JEP 491)では、`synchronized` でもピン留めしない。

## 方式の比較
| 観点 | A: 共有の IO | B: limitedParallelism(16)(採用) | C: 裏で取り直す | D: 仮想スレッド |
|---|---|---|---|---|
| IdP が遅いとき、DB の処理を待たせない | ×(計測) | ○(計測) | ○ | ○(計測) |
| IdP が止まっている間に塞ぐスレッドの数 | 同時の検証の数(IO の上限まで) | 16 まで | 0 | 実際のスレッドは塞がない(仮想スレッドの数は同時の検証の数) |
| 実装の変更 | なし | 1 行と設定の項目 | 大きい。Nimbus のキャッシュを使わず、取得・期限・失敗の扱いを自分で書くことになる | 小さい。ただし executor の作成と終了の管理が増える |
| 版や環境への依存 | なし | なし(kotlinx.coroutines の標準) | なし | JDK 21 ではピン留めの有無が経路のコードで変わる。今は 0 件だが、Nimbus や JDK の版を上げるたびに確かめる必要がある |
| 期限が切れていない間の振る舞い | Nimbus の `refreshAheadCache` が、期限の 30 秒前から裏で取り直すので、要求は待たない(どの方式でも同じ) | 同左 | 同左 | 同左 |

- C はすでに一部が入っている。Nimbus の `refreshAheadCache` は、期限の前に裏で取り直す。要求が取得を待つのは、要求がないまま期限が切れたときか、未知の `kid` で取り直すときだけ。
- B と D はどちらも計測で効いた。B は標準の部品だけで済み、塞ぐスレッドの数に上限があり、JDK の版による違いもない。そのため B を採った。D は、JDK 24 以降に上げるときに、もう一度比べる候補にする。

## CI で確かめていること(時間に左右されない性質)
`platform/security` の `JwtVerifierDispatcherSpec`(通常の `test`。待ち時間の数値で合否を決めない):
- **IdP の取得を止めたまま、IO の上限の 2 倍の検証を待たせても、共有の `Dispatchers.IO` の上限の数のブロッキングの処理を、同時に動かせる。**
  - 合否は、全部がそろったかどうか(ラッチ)で決める。待ち時間では決めない。
  - 待つ時間の上限(20 秒)は、性質が崩れたときに、テストを止めずに失敗させるためのもの。
  - 共有の `Dispatchers.IO` に戻すと、このテストが失敗することを確かめた(28 秒で失敗)。
- **未知の `kid` のトークンを同時に 200 件送っても、JWKS の取得は 2 回まで**(取り直しの頻度の制限。すべて 401)。
