# ADR-0031: 注文の分析(batch-etl)のデータの流れ・日の区切り・照合
- Status: Accepted
- Date: 2026-10-14
- Framework 参照章: 7.1, 7.3, 7.4, 8, 12.3

## Context
ROADMAP P08 は、受注のデータを分析の DB(PostgreSQL を DWH と見立てる)に ELT / ETL で取り込み、再実行しても重複・欠損がないこと、週次の Full 照合でずれを検知することを求める(Framework 7.3・7.4)。決めることは次のとおり。
- 取り込みの元(CLAUDE.md §8 は、ほかのサービスの DB を直接読むことを禁じる)。
- 「1 日」の区切り(分析の日次のパーティションと、照合の元の日次の集計がずれないように)。
- 照合の元と、比べる値。

このフェーズの残りの決定(遅れて届いたデータ・Kafka の保持期間・取り込みと変換の方式)は、P08 のサブ PR ③〜⑤ でこの ADR に足す。DAG の実行の部品(`platform/batch`)は ADR-0030。

## Decision
### 1. 1 日の区切りは日本時間(Asia/Tokyo)
- 「1 日」は **日本時間の 00:00 から翌日の 00:00 まで**(UTC では前の日の 15:00 から)。分析の日次のパーティション(`batch-etl`)と、order-service の日次の集計(§3)は、同じこの区切りを使う(照合がずれないように)。
- 時刻の保存と受け渡しは、これまでどおり UTC の `Instant`(ADR-0011 §8)。日付にするときだけ、日本時間に変換する(order の domain の `BusinessDay`)。
- 理由:
  - 業務の日(売上の締め・日次の報告)は、日本の業務の日。UTC で区切ると、日本時間の 0 時〜9 時の注文が前の日に入り、日次の売上が業務の感覚とずれる。
  - レガシーの受注も日本時間で動いている(ADR-0026 §8)。P09 の日次の売上ファイルも、業務の日で作る。
  - 日本には夏時間がないので、1 日は常に 24 時間。日の境目の扱い(重複する・欠ける時刻)が起きない。
- 区切りのタイムゾーンは、集計の API の応答(`timeZone`)と契約に明記する。

### 2. 取り込みの元は注文のイベント(INT-SALES-002)
- 分析は order-service の DB を直接読まない(CLAUDE.md §8)。注文のイベント(`sales.order.created.v1`・`sales.order.cancelled.v1`)と、**受け付けの後の状態の遷移(`sales.order.status-changed.v1`。P08 で追加)** を Consumer Group `batch-etl.order-ingest` で読む。
  - ADR-0029 §8 は、CONFIRMED / SHIPPED のイベントを「購読者が出てきたら契約に足す」としていた。分析がその購読者。
  - `status-changed` は、状態の遷移と同じトランザクションで Outbox に書く(ADR-0007)。取消も遷移として出す(取消の理由は `sales.order.cancelled.v1`)。
  - ペイロードに遷移の後の **版(楽観的ロックの版)** を入れる。受信側は版の大きいほうを今の状態とし、届く順(トピックが違うと順序は保証されない)に依存しない。

### 3. 週次の照合の元は order-service の日次の集計(件数とハッシュ)
- `GET /v1/order-summaries/daily/{date}`(INT-SALES-001)。§1 の 1 日に受け付けた注文の件数と、内容のハッシュを返す。個々の注文の内容は返さない。
- **認証は必須。スコープは `sales.order:report`**(注文の日次の集計の参照)。読み取り(`sales.order:read`)・書き込みのスコープでは読めない(403)。分析は個々の注文を読む必要がないので、読み取りのスコープを渡さない(最小権限。Framework 12.3)。
- ハッシュの作り方(契約に明記。分析も同じ作り方で計算して比べる):
  - 注文ごとに `{orderId}\t{status}\t{totalAmount.minorUnits}\t{currency}` の 1 行(`status` は今の状態)。
  - 行を注文 ID の **バイト順(UTF-8)** に並べ、`\n` でつなぐ(最後の行の後には付けない)。その SHA-256 を小文字の 16 進で返す。注文がなければ空のバイト列の SHA-256。
  - バイト順を SQL で明示する(`ORDER BY id COLLATE "C"`)。DB の既定の照合順序が言語的な並び(大文字小文字・記号を区別しない)だと、分析の側と並びが変わる。ローカルの PostgreSQL(Alpine。musl の en_US.utf8)の既定はたまたまバイト順と同じになるので、統合テストは ICU の言語的な並びの DB で確かめる。
- 件数とハッシュの両方を比べる。件数だけでは、取りこぼしと重複が打ち消し合う場合と、状態・金額のずれを検知できない。

## Alternatives Considered
- **UTC で区切る**: 実装は単純だが、日本の業務の日とずれる(§1)。不採用。
- **区切りを利用者・テナントごとに設定する**: このリポジトリの業務は日本だけで、要件がない。不採用(必要になったら、集計の API に `timeZone` の引数を足す)。
- **order-service の DB を読み取り専用のロールで直接読む**(ROADMAP の「受注 DB → 分析 DB」の字面どおり): Shared Database の禁止(CLAUDE.md §8)の例外になる。ADR-0027 の例外は改修できないレガシーのためのもので、自分たちのサービスには当てはまらない。不採用。
- **抽出の REST API(ページング)で全件を読む**: 照合のたびに全件を転送する。件数とハッシュの比較で足りる。不採用。
- **照合で読み取りのスコープ(`sales.order:read`)を使う**: 分析に個々の注文を読む権限を渡すことになる。不採用。

## Consequences(トレードオフ)
- order-service のイベントが 1 種類増える(状態の遷移ごとに Outbox の行が 1 つ増える)。
- 集計の API は、その日の注文を全部読んでハッシュを計算する(受け付けの時刻の索引を足した。`V4__orders_ordered_at_index.sql`)。1 日の注文の量が大きくなったら、日ごとの集計を先に作っておく方式を検討する。
- 今日の集計は、その後の注文と遷移で変わる。照合は、遷移が落ち着いた過去の日を対象にする(⑤ で決める)。
- Keycloak の realm にスコープ `sales.order:report` を足した(ADR-0019 改訂履歴)。前に作ったローカルのボリュームには反映されないので、`make clean` が要る。
