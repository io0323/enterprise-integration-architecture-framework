# ADR-0048: Tier 別の NFR の計測(方法・環境・判断)
- Status: Accepted
- Date: 2026-11-07
- Framework 参照章: 13, 14, 16, 18
- 関連: ADR-0045 §4・§5(`caller_deadline` のしきい値と INT-SALES-001 の SLO の差を持ち越した)、ADR-0043 §9(複雑度の枠)、ADR-0017(手元の 1 台での計測の扱い。`docs/reports/p04a-audit-throughput.md`)、ADR-0008(縮退する範囲)、ADR-0029(注文 Saga)、#199、#213、#215

## Context
ROADMAP P14 は、Tier 別の NFR(Framework 18 章)の計測レポート(`docs/reports/p14-nfr.md`)を求めている。ADR-0045 は、`caller_deadline` のアラートのしきい値(1%)と、INT-SALES-001 のカタログ(99.95% / p99 500ms)と Framework の Tier 1(99.99% / p99 300ms)の差の判断を、この計測の後に持ち越した。ADR-0043 §9 の複雑度の枠(大きさ 1000、毎秒 60)も、測定の根拠のない初期値だった。

最初は、手元の 1 台(Apple M3、8 コア、メモリ 8 GiB。Docker の VM に CPU 8・メモリ約 7.75 GiB)で測った(2026-11-07)。

- 基盤を起動する前の確認(load average の上限はコア数の半分の 4)で、ほかのプロジェクトのコンテナなどの外からの負荷を除いた。
- 基盤(`order saga bff`)は何もしていなくても負荷が高い。load average は、起動の前 3.31、起動の約 5 分後 9.64、約 20 分後 6.7〜8.1(一時的に 14.5)。そのため、起動した後の上限を 10 にした。
- 構成は通常のまま(Grafana などは止めていない)。計測の間はブラウザを閉じ、IDE は開いたままにした。

この環境では、次の問題が出た。

- ホストのスワップを 5.9 GB(7.2 GB 中)使っていた。
- 単一ノードの Kafka が高い負荷の中で heartbeat を送れずに切り離され、Kafka Connect のコネクタが既定 5 分の間 UNASSIGNED になった(この間の注文が Saga の期限切れで取り消された。#215)。手元で `./gradlew build` を動かすだけでも切り離された。
- `E2E=1`(Toxiproxy)の構成では、在庫と出荷の gRPC が遅延を入れる前から p99 0.5〜4.7 秒になり、計測の途中にも Kafka が切り離された。`caller_deadline` のしきい値を見直す計測にならなかった。
- 回ごとの差が大きかった(例: 注文の POST の p99 が 1,207 / 661 / 540ms。起動の直後の回が大きく遅い)。

## Decision
### 1. 計測は手動。主な値は GitHub Actions の標準のランナーで取る
- **計測は手動でだけ動かす。** 時間を測る値を合否に使わないため、`./gradlew build`・PR の CI・Ruleset の必須チェックには入れない。
- **主な値は、`.github/workflows/nfr.yml`(`workflow_dispatch`)で取る。** 標準のランナー(4 コア・16 GB。公開リポジトリなので追加の費用はない)の上で、A(`order saga bff`)・B(`cdc iot saas`)・C(`order saga bff`、`E2E=1`)を別のジョブで並列に測る。標準のランナーはジョブごとに別の仮想マシンなので、互いの負荷は影響しない。
- 結果の JSON と環境の記録は、成果物(`nfr-a`・`nfr-b`・`nfr-c`、90 日)に残す。レポートは成果物をもとに書き、成果物の JSON をリポジトリにも残す(90 日で消えるため)。
- 手元の `make nfr-up` と `make nfr-measure` は、補助の手順として残す。手元の値は「ローカルの参照実装での目安」で、本番の性能値ではない(ADR-0017 の計測と同じ扱い)。

### 2. 計測の前後の確認と、環境の記録(`infra/local/scripts/nfr-preflight.sh`・`nfr-postcheck.sh`)
- **基盤を起動する前(`make nfr-up`)**: eiaf の compose プロジェクト以外のコンテナがなく、ホストの 1 分の load average がコア数の半分以下。外からの負荷を除く。
- **計測を始める前(`make nfr-measure`)**:
  - 起動の直後の負荷が落ち着くのを待つ(15 秒ごとに見て、1 分前より 0.2 以上下がらなくなるまで。最長 10 分)。
  - 落ち着いた load average が `NFR_MAX_LOAD`(既定 6)以下。
  - 発行の経路が健全: Kafka Connect のコネクタとタスクがすべて RUNNING で、直近 5 分の Kafka のログにブローカーの切り離し(heartbeat の時間切れ)がない。
  - 満たさなければ止める(`NFR_FORCE=1` で警告だけにして続けられるが、その旨をレポートに書く)。
- **計測の後**: 計測の間に Kafka が切り離された、またはコネクタが RUNNING でなくなった回は、結果の JSON に `pipelineCheck.usable: false` を付け、レポートに使わない。計測の前の確認だけでは、計測の途中の切り離しを見落とす(手元の C で起きた)。
- **環境の記録**: 時刻・コミット・ホスト・CPU の機種(`lscpu`。同じ大きさのランナーでも実行ごとに機種が違うことがあり、回ごとの差が機械の違いかを見分けるため)・load average と上限・負荷の落ち着き・Docker の CPU とメモリ・動いていたコンテナのメモリと CPU。秘密情報は書かない。
- **各シナリオは少なくとも 2 回測る。** 回ごとの差が大きければ、その旨をレポートに書き、1 回だけの値をそのまま使わない。

### 3. Gateway の枠は、計測の間だけ上げる
`make nfr-measure` の中でだけ、`EIAF_RATE_LIMIT_CLIENTS` でクライアントごとの枠を 1,000,000 に上げて Gateway を作り直し、終わったら(失敗・中断でも)通常の値で作り直す。`.env` は書き換えない。数値は **「Gateway の枠で止められない状態での、サービス側の性能」** で、レポートに使った枠の値を書く。Webhook のルートの枠(remote_addr ごとに 60 秒 120 件)は変えず、その枠に収まる間隔で送る。

### 4. 遅延の測り方
- イベントの遅延は、イベントが運ぶ時刻の差で出す: CloudEvents の `ce_time` と Kafka のレコードの時刻(Outbox → Kafka)、前のメッセージと次のメッセージの `ce_time`(Saga の各段)、CDC の `source.committedAt` とレコードの時刻。どれも Docker の時計なので、ホストとの時計のずれが入らない。IoT と Webhook は、送った時刻と Kafka で読めた時刻(どちらもホストの時計)で出す。
- Saga は、注文ごとの相関 ID(`X-Correlation-Id` → `correlationid` ヘッダ)でイベントと注文を対応づける。対応づかなければ計測を止める。
- Gateway の値は Prometheus のヒストグラムから出す。計測の窓は、慣らしの送信を Prometheus が 1 回 scrape してから始める(作り直した直後の Gateway の系列は 0 から始まり、窓の前の値がないと増分を取りこぼすため)。
- 計らない慣らしの送信をしてから測る。画面(storefront・caller-deadline)は、gRPC の提供側の最初の呼び出しが遅く BFF の Circuit Breaker が開くので、15 秒ずつ送り、完全な応答が 95% 以上の回が出るまで慣らす(最長 2 分。#199 と同じ種類)。
- 送り方は 2 通り: 注文 API は並列の数を決めて送り続ける(上限に近い負荷)。画面・Webhook・IoT は予定の時刻に送る(open loop。遅くなっても送る量が減らない)。

### 5. レポートの連携の一覧は、カタログから作って build で確かめる
レポートの「連携ごとの結果」の表は、`scripts/reports/nfr-table.py --write` がカタログと `docs/reports/p14-nfr-integrations.json` から作る。カタログのすべての連携が表と JSON に載っていることは `./gradlew build`(tools/architecture-test の `NfrReportSpec`)が確かめる。**確かめるのは一覧の一致だけで、計測の数値は確かめない。** 計測しない連携も、理由とともに載せる。ADR-0008 で範囲外・縮退とした項目もレポートに載せる。

### 6. 計測のコードは `tests/e2e` の `measurement` ソースセットに置く
- E2E の部品(`E2eEnvironment` など)を使うため、`e2eTest` に `associateWith` する。`check` でコンパイルするが、build・CI では実行しない(`:tests:e2e:measureNfr` を手動で動かす)。
- Konsist のアーキテクチャのテストは、`measurement` を本番に載らないソースセットとして扱う(Kafka・Avro を直接使う)。

### 7. 計測の結果からの判断
根拠は `nfr` の [run 42369263281](https://github.com/io0323/enterprise-integration-architecture-framework/actions/runs/42369263281)(2026-11-07、`runs=2`、12 回すべて `usable: true`)。結果は `docs/reports/p14-nfr/runner/`、表は `docs/reports/p14-nfr.md`。

#### 7.1 INT-SALES-001: カタログの値(99.95% / p99 500ms)のまま変えない
| | 1 回目 | 2 回目 |
|---|---|---|
| 負荷 | 並列 16、247 件/秒 | 並列 16、360 件/秒 |
| POST の p99(クライアント) | 239ms | 177ms |
| GET の p99(クライアント) | 67ms | 45ms |
| Gateway の p99(ヒストグラム) | 414ms | 184ms |
| 5xx | 0 件 | 0 件 |

- カタログの 500ms は 2 回とも満たした。Framework の Tier 1 の 300ms は、クライアントでは満たしたが、Gateway では 1 回目に超えた。並列 16 で送り続けた上限に近い負荷で、共有の 4 コアのランナーでは 300ms との差が安定しない。
- 可用性(99.95% と 99.99%)は、数分の計測では確かめられない。
- カタログを 300ms にすると、SLO のルールとアラート(ADR-0045。`AlertGovernanceSpec` がカタログとの一致を確かめる)も変わる。根拠が安定しない値で、参照実装の SLO を厳しくしない。
- **Framework の 99.99% / 300ms は、本番の目標として残す。** この参照実装を採用する側が、自分の基盤で測り直してカタログを厳しくする。差はレポートの表に「カタログは満たした。Framework の 300ms は Gateway の 1 回目で超えた」と残す(ADR-0045 §5 の持ち越しを閉じる)。

#### 7.2 複雑度の枠: 大きさ 1000・毎秒 60 のまま変えない
- 枠を超える送り方(1 クライアントが複雑度 7 を毎秒 15 件 = 毎秒 105 を 60 秒、900 件)では、2 回とも 636 件が通り、264 件が 429 になった。計算の上限(枠の 1000 と 60 秒 × 60 の戻りで約 657 件)に近く、枠は設計どおりに効いている。手元の 4 回(637〜656 件)とも合う。
- 枠に収まる送り方(注文 1 件の詳細を毎秒 8 件 = 複雑度 56 / 秒、20 件の一覧を毎秒 0.4 件 = 56 / 秒)では、429 は 0 件だった。
- 実際のクエリの分布がないので、値を変える根拠はない。本番の流量で決め直す(ADR-0043 §9 のとおり)。

#### 7.3 `caller_deadline` のしきい値: 1% のまま変えない。部分応答は別の SLI で見る
C(bff-graphql → Gateway に Toxiproxy で揺れのある遅延。画面の詳細を毎秒 6 件 × 90 秒)の結果:

| 遅延 | `caller_deadline`(注文 API) | 部分応答 | 1 秒を超えた割合 |
|---|---|---|---|
| なし | 0% / 0% | 0% / 0% | 0% / 0% |
| 600±400ms | 0% / 0% | 0% / 0% | 2.4% / 1.5% |
| 1000±600ms | 1.39% / 1.04% | 7.6% / 6.9% | 53% / 50% |
| 1300±600ms | 0.18% / 0.18% | 94% / 68% | 8.3% / 37% |

- `caller_deadline` が増えるのは、注文 API の 1 回の試行が試行の上限(1.5 秒)と注文の取り分(2 秒)の間にかかる帯だけだった。それより遅いと、試行の時間切れ(`kind="attempt"`)と Circuit Breaker の拒否が先に起き、`caller_deadline` はほぼ 0 に戻る。**`caller_deadline` は「予算の配分が依存先の遅さに合っていない」ことを示す診断の信号で、利用者への影響の大きさは表さない。**
- 普段の負荷(遅延なし。ランナーの storefront と C の 4 回、手元の storefront の 4 回)ではどれも 0% で、帯ではランナーの 3 回(この 2 回と、`runs=1` の試しの回 run 42357857825)が 1.04〜2.85%。1% は、普段と帯を分ける値として妥当なので、変えない。
- **遅延が大きいときの部分応答(68〜94%)は、どのアラートにも映らない。** 部分応答は速い 200 なので、画面の可用性(5xx)にも遅延(1 秒超)にも数えられない。部分応答の割合を画面の SLI にすることを、別の Issue で検討する(レポートの既知の問題 4)。

#### 7.4 ランナーでの計測の前の確認の上限
- 基盤を起動する前の上限(コア数の半分 = 2)は、ランナーの準備の直後の負荷(1.3〜3.7)で何度か待ったが、どのジョブも 1〜2 分で通った。
- 起動した後に何もしていないときの load average は 0.43〜1.71(手元は 7〜10)。run 42369263281 は、当時の既定の上限 6 のまま測った。どの回も実際の値を環境の記録に残している。
- **ランナーの起動した後の上限(`nfr` の入力 `max_load`)の既定は 2 にする。** 決め方は、手元で 10 にしたときと同じで、基盤が何もしていないときの実測の上の端に余裕を足す。
  - 実測: `runs=1` の run 42357857825 で、計測を始める前に落ち着いた値が 0.43〜1.19(6 回)。上の端の 1.19 に約 0.8 の余裕を足して 2 にした。`runs=2` の run 42369263281 で見えた最大の 1.71 も収まる。
  - 6 では、ランナーではほかの負荷が残っていてもほとんど止まらない。2 なら、準備の負荷が残っているときだけ止まる。
  - 手元で使う `make nfr-measure` の既定(`NFR_MAX_LOAD` の 6)は変えない。手元では基盤が何もしていなくても 7〜10 あり、手元の値は付録の参考の扱いのため(手元で測るときは、その台の実測から決めて `NFR_MAX_LOAD` で渡す)。

## Alternatives Considered
- **手元の 1 台だけで測る**: 採らない。メモリ 8 GiB のホストではスワップを使いながら動き、Kafka が切り離され、C を測れなかった。
- **ローカルの Kafka の設定を変える(`broker.session.timeout.ms` を延ばす)・基盤を軽くする**: 採らない。測る対象の設定や構成を、計測のために変えることになる。
- **計測を PR の CI に入れる**: 採らない。時間を測る値は、ランナーの機種や混み具合で変わるので、合否に使わない。
- **大きいランナー(有料)**: 採らない。標準のランナーで、手元の問題(メモリ)は解ける。
- **A・B・C を 1 つのジョブで順に測る**: 採らない。前の段の負荷やデータが残り、時間も約 3 倍かかる。

## Consequences(トレードオフ)
- 主な値は GitHub の標準のランナー(Linux。Docker は VM を挟まない)の値で、手元の Docker Desktop とも本番とも条件が違う。どちらの値も本番の性能値ではなく、目安として扱う。
- ランナーの CPU の機種は実行ごとに変わりうる。環境の記録の `lscpu` で見分ける。
- 成果物は 90 日で消えるので、レポートに使った結果の JSON はリポジトリに残す。
- 計測の前の確認で止まると、その回は測れない(ランナーでは 10 分まで落ち着くのを待つ)。
- 手元の `./gradlew build` は基盤の Kafka を切り離すことがある。手元で測るときは、計測の前後に重い処理を動かさない(計測の前の確認が直近 5 分の切り離しを見る)。
