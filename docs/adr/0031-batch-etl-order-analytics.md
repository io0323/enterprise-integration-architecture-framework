# ADR-0031: 注文の分析(batch-etl)のデータの流れ・日の区切り・照合
- Status: Accepted
- Date: 2026-10-14
- Framework 参照章: 7.1, 7.3, 7.4, 8, 12.3

## Context
ROADMAP P08 は、受注のデータを分析の DB(PostgreSQL を DWH と見立てる)に ELT / ETL で取り込み、再実行しても重複・欠損がないこと、週次の Full 照合でずれを検知することを求める(Framework 7.3・7.4)。決めることは次のとおり。
- 取り込みの元(CLAUDE.md §8 は、ほかのサービスの DB を直接読むことを禁じる)。
- 「1 日」の区切り(分析の日次のパーティションと、照合の元の日次の集計がずれないように)。
- 照合の元と、比べる値。

取り込みと変換の方式(§4)と遅れて届いたデータ(§5)は P08 ③、週次の照合(§6)は ④、Kafka の保持期間と回復(§7)は ⑤ で足した。DAG の実行の部品(`platform/batch`)は ADR-0030。

## Decision
### 1. 1 日の区切りは日本時間(Asia/Tokyo)
- 「1 日」は **日本時間の 00:00 から翌日の 00:00 まで**(UTC では前の日の 15:00 から)。分析の日次のパーティション(`batch-etl`)と、order-service の日次の集計(§3)は、同じこの区切りを使う(照合がずれないように)。
- 時刻の保存と受け渡しは、これまでどおり UTC の `Instant`(ADR-0011 §8)。日付にするときだけ、日本時間に変換する(order の domain の `BusinessDay`)。
- 理由:
  - 業務の日(売上の締め・日次の報告)は、日本の業務の日。UTC で区切ると、日本時間の 0 時〜9 時の注文が前の日に入り、日次の売上が業務の感覚とずれる。
  - レガシーの受注も日本時間で動いている(ADR-0026 §8)。P09 の日次の売上ファイルも、業務の日で作る。
  - 日本には夏時間がないので、1 日は常に 24 時間。日の境目の扱い(重複する・欠ける時刻)が起きない。
- 区切りのタイムゾーンは、集計の API の応答(`timeZone`)と契約に明記する。

### 2. 取り込みの元は注文のイベント(INT-SALES-002)
- 分析は order-service の DB を直接読まない(CLAUDE.md §8)。注文のイベント(`sales.order.created.v1`・`sales.order.cancelled.v1`)と、**受け付けの後の状態の遷移(`sales.order.status-changed.v1`。P08 で追加)** を Consumer Group `batch-etl.order-ingest` で読む。
  - ADR-0029 §8 は、CONFIRMED / SHIPPED のイベントを「購読者が出てきたら契約に足す」としていた。分析がその購読者。
  - `status-changed` は、状態の遷移と同じトランザクションで Outbox に書く(ADR-0007)。取消も遷移として出す(取消の理由は `sales.order.cancelled.v1`)。
  - ペイロードに遷移の後の **版(楽観的ロックの版)** を入れる。受信側は版の大きいほうを今の状態とし、届く順(トピックが違うと順序は保証されない)に依存しない。

### 3. 週次の照合の元は order-service の日次の集計(件数とハッシュ)
- `GET /v1/order-summaries/daily/{date}`(INT-SALES-001)。§1 の 1 日に受け付けた注文の件数と、内容のハッシュを返す。個々の注文の内容は返さない。
- **認証は必須。スコープは `sales.order:report`**(注文の日次の集計の参照)。読み取り(`sales.order:read`)・書き込みのスコープでは読めない(403)。分析は個々の注文を読む必要がないので、読み取りのスコープを渡さない(最小権限。Framework 12.3)。
- ハッシュの作り方(契約に明記。分析も同じ作り方で計算して比べる):
  - 注文ごとに `{orderId}\t{status}\t{totalAmount.minorUnits}\t{currency}` の 1 行(`status` は今の状態)。
  - 行を注文 ID の **バイト順(UTF-8)** に並べ、`\n` でつなぐ(最後の行の後には付けない)。その SHA-256 を小文字の 16 進で返す。注文がなければ空のバイト列の SHA-256。
  - バイト順を SQL で明示する(`ORDER BY id COLLATE "C"`)。DB の既定の照合順序が言語的な並び(大文字小文字・記号を区別しない)だと、分析の側と並びが変わる。ローカルの PostgreSQL(Alpine。musl の en_US.utf8)の既定はたまたまバイト順と同じになるので、統合テストは ICU の言語的な並びの DB で確かめる。
- 件数とハッシュの両方を比べる。件数だけでは、取りこぼしと重複が打ち消し合う場合と、状態・金額のずれを検知できない。

### 4. 取り込み(ETL)と変換(ELT)
日次の DAG `batch-etl.order-daily`(パーティション = §1 の業務の日。ADR-0030)は、取り込み → 変換の順に動く。DB は batch-etl の DB(PostgreSQL を DWH と見立てる)。

| スキーマ | 中身 | 書き方 |
|---|---|---|
| `raw` | 取り込んだイベント(受け付け・状態の遷移・取消) | 自然なキー(注文 ID・注文 ID と版)で冪等に追加(`ON CONFLICT DO NOTHING`) |
| `etl` | 作り直しの印(データが変わった業務の日) | 取り込みと同じトランザクション |
| `mart` | 日次のパーティション `mart.order_daily`(注文ごとに今の状態) | 日ごとに置換 |
| `batch` | 実行の記録・Watermark(ADR-0030) | — |

- **取り込み(Incremental Load)**: 注文のイベント(§2)を、前回の位置(トピック・パーティションごとの次のオフセット)から、始めた時点の末尾まで読む。
  - **行・作り直しの印・位置(バッチの Watermark `order-events.positions`)を 1 つのトランザクションで確定する**。途中で kill されても、次の実行は確定した位置から読み直し、行は冪等なので重複しない。
  - 取り込みの正は DB の位置。Consumer Group(`batch-etl.order-ingest`)にもコミットするのは lag の監視のため(⑤ のアラート)。
  - 読めない値(tombstone・形式の誤り)は、受け取ったバイト列のまま DLQ(`{topic}.dlq`)に送って先に進む(ADR-0028 と同じヘッダ)。スキーマのレジストリが一時的に使えないときは、DLQ に送らずに失敗にする(リトライ・次の実行)。
  - 保存した位置のイベントがトピックの保持期間を過ぎて消えていたら、**黙って先に進まずに失敗にする**(`auto.offset.reset=none`)。先に進むと取りこぼしになるため。回復は ⑤ の Runbook。
- **ETL(機密項目はロードの前に変換する。Framework 7.1)**: 届け先の住所は個人情報なので、**取り込む前に地域(国・都道府県・郵便番号の先頭 3 桁)に変える**(domain の `ShippingArea`)。市区町村・番地・建物は分析の DB のどこにも入れない(統合テストで確かめる)。分析に番地の粒度は要らない。
- **ELT(それ以外。Framework 7.1 の既定)**: 受け付け・遷移・取消はそのまま `raw` に入れ、日次のパーティションは SQL で作る。今の状態は版の最も大きい遷移(なければ PLACED)。取消の理由は取消のイベントから。
- **パーティションの置換(再実行安全。Framework 7.4)**: 1 つのトランザクションで、その日の行を消して `raw` から入れ直し、その日の印を消す。何度実行しても結果は同じ。日ごとにトランザクションを分けるので、途中で止まっても作り直した日は正しく、残りは再実行で作る。
  - 作り直しの間は印の表を `SHARE ROW EXCLUSIVE` でロックする。取り込みの印の追加はロックが外れるまで待つので、作り直しが読んだ後に届いた行の印は、印を消した後に付き、次の実行で作り直される(取りこぼさない)。
- 業務の日は、受け付けの時刻から domain の `BusinessDay`(§1)で決めて `raw` に保存する(SQL の時刻の変換に依存しない)。
- **起動と SLA**: `batch-etl serve` が、毎日 01:00(日本時間。`BATCH_ETL_DAILY_AT`)に前日の分を起動し、翌日の 06:00(`BATCH_ETL_SLA_AT`)を期限にする(ADR-0030 §4・§6)。止まっていた間の分は直近の 1 回だけ取り戻し、それより前の日・失敗した日は運用者が `batch-etl run <yyyy-MM-dd> [--restart]` で実行する(docs/runbooks/batch-rerun.md は ⑤)。

### 5. 遅れて届いたデータ
パーティションを作った後に、その日の注文のデータが変わることがある(出荷・配達・取消の遷移、障害で遅れて届いた受け付け)。
- 取り込みで、**新しく入った行の業務の日に作り直しの印を付ける**(遷移・取消は、その注文の受け付けの日。受け付けがまだ届いていなければ、受け付けが届いたときに付く)。同じイベントを読み直しても行が増えないので、印も付かない。
- 日次の実行(業務の日 D)の変換は、**D と、印の付いた日のうち D から 31 日前まで** を古い順に作り直す(`LateDataPolicy.REBUILD_WINDOW_DAYS`)。
  - 31 日にした理由: 注文の遷移(出荷・配達・取消)はおおむね受け付けから 1 か月以内に終わる。月次の締め(前月分)の前に、前月の全日が作り直されるようにする。日次の実行が作り直すのは印の付いた日だけなので、毎日 31 日分を作り直すわけではない。
- **31 日より古い日は自動では作り直さない**。印は残し、実行の報告(`tooOld`)に入れる(⑤ でメトリクス・アラートにする)。運用者がその日を明示的に作り直す(`RunMode.RESTART`。docs/runbooks/batch-rerun.md)。古い日を自動で作り直すと、締めた後の数字が知らないうちに変わるため。
- D より後の日(まだ終わっていない日の分)の印は、その日の実行に任せる。
- 統合テスト `BatchEtlIT`「遅れて届いたデータ」で、D の後から届いた遷移・受け付けが次の実行で D に入り、40 日前の受け付けは作り直されずに印が残ることを確かめる。

### 6. 週次の Full 照合
差分の取り込み(§4)のずれ(取りこぼし・重複・状態のずれ)を、order-service の日次の集計(§3)との件数とハッシュの突合で検知する(Framework 7.3)。
- **DAG** `batch-etl.order-reconcile`(パーティション = 実行の日)。毎週月曜 07:00(日本時間。`BATCH_ETL_RECONCILE_ON` / `_AT`)に起動する。日次の DAG の SLA の期限(06:00)の後。運用者は `batch-etl reconcile <yyyy-MM-dd> [--restart]` で実行する(一致しない日があれば終了コード 3)。
- **範囲**: 実行の日の前日から 38 日前まで(`ReconcilePolicy.DAYS`)。遅れて届いたデータを自動で作り直す 31 日(§5)に 1 週間を足し、自動で作り直さなくなった直後の週も 1 回は比べる。今日は終わっていないので含めない。
- **手順**: 比べる前に今の末尾まで取り込む。一致しない日は、もう一度取り込み、31 日以内の日なら作り直してから比べ直す(取り込みと問い合わせの間に届いたイベントで、ずれと判定しないため)。31 日より古い日は作り直さずに比べ直す(締めた後の数字を自動で変えない。§5)。比べ直しても一致しなければ **DRIFT**。
- **DRIFT は自動では直さない**。取りこぼし(DLQ に入った・保持期間で消えた)は、raw からの作り直しでは戻らないため。結果を `mart.reconciliation` に残し、メトリクス `eia.batch_etl.reconcile.drift_days` を出す(アラートと Runbook は ⑤)。
- **呼び出し**: order-service には **API Gateway 経由**で問い合わせる(`/sales/v1/order-summaries/daily/{date}`。CLAUDE.md §5: API は Gateway 経由)。
  - 認証は Client Credentials のトークン(クライアント `eiaf-batch-etl`。スコープ `sales.order:report` だけ。ADR-0019 改訂履歴)。
  - Timeout(1 回 30 秒・全体 2 分)・Retry(408・429・502〜504・接続の失敗)・Circuit Breaker(ADR-0021)。401 はトークンを取り直してリトライする。
  - **Fallback**: 問い合わせられない日は **UNVERIFIED** にしてほかの日を比べ続け、結果を記録してから一時的な失敗を返す(platform/batch のリトライ・次の再実行で比べ直す)。集計の値を推測で埋めない。パーティションをまだ作っていない日も UNVERIFIED(比べない)。
  - 応答の `timeZone` が分析の区切り(Asia/Tokyo。§1)と違えば、比べずに失敗にする(区切りのずれた集計を比べない)。
- 分析の側のハッシュも §3 と同じ作り方(`ORDER BY order_id COLLATE "C"`。統合テストは ICU の言語的な並びの DB で確かめ、`COLLATE "C"` を外すと失敗することを確かめた)。

### 7. Kafka の保持期間と、保持期間を超えた回復
- 注文のイベントのトピック(`sales.order.created.v1`・`cancelled.v1`・`status-changed.v1` と DLQ)の保持期間は **14 日**(`infra/local/kafka/topics.conf`。ほかのイベント・コマンドの既定の 7 日より長い)。
- **14 日にした理由**: 次の両方より長くする。
  1. **batch-etl が止まりうる最も長い期間**: 連休(年末年始・大型連休で最大 9 日)の間、障害に気づいても直せないことがある。9 日に余裕を足す。
  2. **週次の照合の間隔(7 日)**: 照合でずれを見つけてから原因を調べる間に、取り込み残し・DLQ のイベントが消えないようにする。
  - これらのトピックを読むのは batch-etl だけ(INT-SALES-002 の consumers)。冪等消費の記録(processed_message)の保持期間には影響しない(batch-etl は自然なキーで冪等にしている)。
- **保持期間に近づいたら知らせる**: Prometheus の保持期間(ローカルは 3 日)は Kafka の保持期間より短く、Kafka のオフセットの変化からは数日前からの遅れを判定できない。そこで batch-etl が 5 分ごとに Kafka を見て、次のメトリクスを出す(`KafkaIngestPositions`)。
  - 取り込み残しの最も古いイベントの経過時間(`eia_batch_etl_ingest_lag_age_seconds`)。
  - トピックの保持期間(`eia_batch_etl_ingest_retention_seconds`)。
  - 消えた件数(`eia_batch_etl_ingest_lost_events`)。

  アラートの閾値は保持期間に対する割合にする(50% で warning・75% で critical。保持期間を変えると閾値も追従する。`prometheus/rules/batch.rules.yml` と promtool のテスト)。batch-etl が止まっていると上のメトリクスが出ないので、Kafka 側からも見る(取り込み残しがあるのに、Consumer Group のオフセットが 2 日進まない。`BatchEtlIngestStale`)。
  - batch-etl の Consumer Group(`batch-etl.order-ingest`)は 1 日 1 回だけコミットする。そのため、常駐の Consumer の停滞・遅れのアラート(`consumer.rules.yml`)の対象から除く。
- **保持期間を超えたら**:
  - 取り込みは黙って先に進まずに失敗する(§4)。
  - 運用者は消えた件数を確かめ、消えた範囲を飛ばして再開する(`batch-etl skip-lost-events --confirm`)。
  - 影響した日は週次の照合で DRIFT として見つける(docs/runbooks/batch-rerun.md の「保持期間を超えた回復」)。
- **消えたイベントを埋め戻す手段は、今はない**(Issue #116)。
  - order-service はイベントを再発行できない(Outbox は発行の後に消える)。
  - 分析は order-service の DB を読まない。
  - 日次の集計の API は件数とハッシュだけを返す。
  - 影響した日は、手段ができるまで DRIFT のまま残る。

### 8. 日次の売上ファイル(INT-SALES-004。P09 ④)
- DAG `batch-etl.sales-file`(ステップ `export`)は、日次の DAG(`batch-etl.order-daily`)の **同じ業務の日が成功したら** 起動する(`Trigger.AfterDag`。ADR-0030 §4)。その日の `mart.order_daily` から、`contracts/files/sales_daily.v1.yaml` の売上ファイルを書いて置く(platform/file-transfer の `FilePublisher`。ADR-0032 §2)。SLA は業務の日の翌日 07:00 JST(日次の SLA の 06:00 の後。`BATCH_ETL_FILE_SLA_AT`)。
- 行は注文 ID のバイト順(`ORDER BY order_id COLLATE "C"`。照合と同じ)で、読み取り専用のトランザクションのカーソルで読み、そのまま書き出しに渡す(その日の行を全部メモリに載せない)。顧客 ID は書かない(契約の「個人情報なし」)。
- 形式は既定で Parquet だけ。CSV + gzip は設定(`BATCH_ETL_FILE_FORMATS=parquet,csv`)で足す。形式ごとに mart を読み直す。
- **ファイルの版(名前)**: `sales_daily_{業務の日の締め(日本時間の翌日 00:00 を UTC で)}_{実行の世代 3 桁}.{ext}`(例 2026-10-14 の 1 世代目は `sales_daily_20261014150000_001.parquet`)。
  - 名前の時刻を「作った時刻」にしないのは、同じ実行のやり直し(ステップのリトライ・落ちた後の再開)で同じ名前にし、上書きするため(再実行安全。Framework 7.4)。
  - 日次の DAG を作り直すと(遅れて届いたデータ。§5 の RESTART)、AfterDag でこの DAG もやり直し、世代が増えるので **新しい版の別のファイル** になる。受け手は、同じ日の新しい版として受け取る(ファイル名が違うので、重複(ADR-0032 §5)にはならない)。
  - 遅れて届いたデータで作り直した **過去の日**(実行の日でない日)は、AfterDag では起動しない(AfterDag は同じパーティションだけ)。必要なら運用者が `batch-etl sales-file <日付> --restart` で新しい版を置く(Runbook は ⑥)。
- マニフェストの traceparent は、書き出しのステップの span(DAG の実行の span の子)。受け手の実行はこれを親にするので、送り手から受け手までが 1 つのトレースにつながる(ADR-0030 §5)。span の外では書き出さない(traceparent がないため)。
- パーティションがまだない日(`mart.partition_build` にない)は書かない(`ConflictError`。0 件のファイルと区別するため)。注文のない日は 0 件のファイルを置く(契約)。
- 置き場は S3 互換ストレージ。受け口の自分の接頭辞(`inbox/sales-daily/`)に書くだけの identity を使う(ADR-0032 §1。`BATCH_ETL_FILE_S3_*`)。`BATCH_ETL_FILE_S3_ENDPOINT` がなければ、この DAG を登録しない(週次の照合と同じ扱い)。compose の設定は P09 ⑥。
- 手動の実行は `batch-etl sales-file <yyyy-MM-dd> [--restart]`。
- コードの形(`SalesDailyLayout`)が契約と一致することは単体テスト(`SalesDailyLayoutSpec`)で、書いたファイルが受け側の検査(`FileVerifier`)に通ることは統合テスト(`SalesFileIT`)で確かめる。

## Alternatives Considered
- **UTC で区切る**: 実装は単純だが、日本の業務の日とずれる(§1)。不採用。
- **区切りを利用者・テナントごとに設定する**: このリポジトリの業務は日本だけで、要件がない。不採用(必要になったら、集計の API に `timeZone` の引数を足す)。
- **order-service の DB を読み取り専用のロールで直接読む**(ROADMAP の「受注 DB → 分析 DB」の字面どおり): Shared Database の禁止(CLAUDE.md §8)の例外になる。ADR-0027 の例外は改修できないレガシーのためのもので、自分たちのサービスには当てはまらない。不採用。
- **抽出の REST API(ページング)で全件を読む**: 照合のたびに全件を転送する。件数とハッシュの比較で足りる。不採用。
- **照合で読み取りのスコープ(`sales.order:read`)を使う**: 分析に個々の注文を読む権限を渡すことになる。不採用。
- **取り込みを常駐の Consumer(`EventConsumer`)で行う**: 鮮度は上がるが、日次の締めの単位(どこまで取り込んだら D を作ってよいか)が分かりにくくなる。日次の DAG の最初のステップで、始めた時点の末尾まで読む(Incremental Load の Watermark がそのまま位置になる)。鮮度の要件が分単位になったら、常駐の取り込みに替える。
- **住所をそのまま `raw` に入れ、mart で落とす(ELT だけ)**: 分析の DB に個人情報が入り、権限・保持・削除の管理が要る。ロードの前に落とす(ETL)。
- **PostgreSQL の宣言的パーティション(日ごとの子表)を ATTACH / DETACH で置換する**: 1 日の件数が小さいうちは、行の削除と追加で足りる。件数が大きくなったら検討する。
- **遅れて届いたデータの作り直しの範囲を無制限にする**: 締めた後の数字が知らないうちに変わる。31 日で区切り、それより古い日は運用者が判断する。
- **照合で order-service を直接(Gateway を通さずに)呼ぶ**: サービスは APISIX からの mTLS だけを受ける(ADR-0024 §6)。分析のための別の入口とクライアント証明書が要る。Gateway 経由にした(JWT の検証・Rate Limit・ログが一か所にそろう)。
- **DRIFT の日を自動で作り直す**: raw にないデータ(取りこぼし)は作り直しでは戻らず、ずれが隠れる。31 日以内の日は比べ直しの前に作り直すので、作り直しで直るずれは DRIFT にならない。残った DRIFT は運用者が原因を調べる。
- **照合で問い合わせられない日を一致とみなす(Fallback で成功にする)**: 照合の意味がなくなる。UNVERIFIED にして再実行で比べ直す。
- **保持期間を無期限・長期(例 90 日)にする**: 取りこぼしは起きにくくなるが、個人情報(届け先の住所)を含むイベントを長く残すことになる。止まりうる期間と照合の間隔から決めた 14 日にし、超えたときの検知と回復の手順を用意する。
- **取り込みの遅れを Kafka のオフセットの変化(kafka-exporter)だけで見る**: Prometheus の保持期間が短く、保持期間(14 日)に近い遅れを判定できない。batch-etl が Kafka から最も古い取り込み残しの時刻を読む。batch-etl の停止は Kafka 側(2 日の停滞)でも見る。

## Consequences(トレードオフ)
- order-service のイベントが 1 種類増える(状態の遷移ごとに Outbox の行が 1 つ増える)。
- 集計の API は、その日の注文を全部読んでハッシュを計算する(受け付けの時刻の索引を足した。`V4__orders_ordered_at_index.sql`)。1 日の注文の量が大きくなったら、日ごとの集計を先に作っておく方式を検討する。
- 今日の集計は、その後の注文と遷移で変わる。照合は、遷移が落ち着いた過去の日を対象にする(④ で決める)。
- 日次の実行は、印の付いた過去の日も作り直すので、遅れて届いたデータが多い日は実行が長くなる(SLA の予測は実績の p90 で追う。ADR-0030 §6)。
- 取り込みは日次の実行の中で行うので、分析の鮮度は 1 日(前日分が翌朝にそろう)。
- Keycloak の realm にスコープ `sales.order:report` を足した(ADR-0019 改訂履歴)。前に作ったローカルのボリュームには反映されないので、`make clean` が要る。
